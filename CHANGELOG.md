# Changelog

All notable user-facing changes should be documented here.

This project follows npm package versions for the `hatchkit` CLI. Dates use `YYYY-MM-DD`.

## Unreleased

### Security

- **No Coolify API token in any repo.** Coolify tokens cannot be scoped below "every app in the team", and hatchkit pushed its own root token into every project's GitHub secrets as `COOLIFY_API_TOKEN` / `COOLIFY_TOKEN`. One leaked Actions log, malicious dependency or workflow bug in any repo could read every app's env on the host and start a container with the host's Docker socket. CI now holds one secret per Coolify application: the HMAC key of that app's manual deploy webhook, which queues a deploy of that one app and can do nothing else. The deploy job picks the image by moving a `:live` tag in its own GHCR package with its `GITHUB_TOKEN`, then signs the webhook. Hatchkit's token stays in the keychain.
- Coolify's manual webhook secrets default to null, and its GitHub, Gitea and Bitbucket endpoints then accept a signature made with the empty key. Every app hatchkit wires now gets a random secret in all four slots.
- `hatchkit secrets isolate <project> | --all [--dry-run] [--rotate]` moves an existing project over: per-app deploy hooks, the workflow's deploy steps rewritten, `:live` seeded and the apps pointed at it when the workflow promotes it, the new secrets pushed, and `COOLIFY_API_TOKEN` / `COOLIFY_TOKEN` / `COOLIFY_WEBHOOK_URL` deleted from the repo once no workflow reads them. `--rotate` mints new per-app secrets. `--app <uuid>[:client|:server]` covers a repo without a manifest.
- The starter's server error reports no longer carry the user's session. `@sentry/node` 10 puts the request headers (`Cookie` included), the parsed cookies (the better-auth session token) and up to 10 KB of the request body on every server event, and leaving `sendDefaultPii` unset does not stop it. `packages/server/src/sentry-options.ts` now stops reading incoming bodies, and strips cookies, the `Cookie`, `Set-Cookie` and `Authorization` headers and the body from every event and transaction. Projects scaffolded earlier keep the old `instrument.ts`; copy the new file and the `Sentry.init` line across.
- `hatchkit doctor` fails a project that holds a provisioner credential in an env file, the plaintext provisioning cache, a Coolify app env, a workflow or the repo's secret names. Values are compared in memory; only key names are printed. It also checks each app's deploy hook, and warns for compose apps, whose "Shallow Clone" setting must be off (with it on, Coolify fetches a webhook's commit by sha, which reaches commits that exist only in a fork).

### Changed

- **Deploys no longer take the site down.** Every hatchkit app used to be a Coolify Docker Compose app. Coolify redeploys those by stopping the old container before it starts the new one, so each push was an outage until the new process listened. Coolify only does rolling updates for Docker Image, Dockerfile, Nixpacks and Static apps with a health check. New projects now get one Docker Image app per service (`coolifyRuntime: "image"` in `.hatchkit.json`, `--coolify-runtime` on `create`). Each app pulls the GHCR image the workflow builds and carries a health check (`/api/health` for the server, `/` otherwise). The old container serves until the new one is healthy, and a new container that never turns healthy is removed with the old one still up. Under the image runtime the server is always its own app, so mongo and redis are Coolify-managed databases in both topologies. Existing manifests without the field stay on `compose`.
- The deploy workflows no longer pin anything on Coolify. They point `<image>:live` at the commit's `<image>:<sha>` in GHCR, and every app pulls `:live`, so one workflow is correct for compose and image apps alike. `hatchkit update` converts an older pin step. The generated `verified-deploy` script promotes and rolls back `:live` the same way; its rollback target is the commit each half served before the run, when the registry still has that image.
- The scaffolded Debian runtime images (`node:*-bookworm-slim`) install `curl`. Coolify's health check runs `curl … || wget …` inside the container, and those images had neither.
- `hatchkit sync` turns on a Docker Image app's health check when it is off, and never overwrites an image app's port or base directory.
- `hatchkit create --yes` now honours `--topology`; the non-interactive path dropped it.
- `hatchkit create` pushes the dotenvx key to every app it provisioned, not only one named after the project — split projects never got it.

### Added

- `hatchkit migrate-runtime` moves a deployed compose app to Docker Image apps, side by side. It copies the image, env, port and every hostname (including hosts named only in hand-written Traefik labels), deploys the new app while the old one serves, checks it through Traefik, then stops the old app and repoints the repo's deploy secret. `--rollback` restores the compose app; `--cleanup` deletes it, keeping its volumes. It refuses apps with a datastore service or a volume, whose data would not follow.
- `hatchkit migrate-runtime --carry-volume <service>=<volume>` moves a compose app that keeps its state in a named volume, for example a SQLite database. The new app mounts the same Docker volume, so no data is copied. Two containers write the volume during verification and during the overlap of every later rolling deploy, and the plan says so. On Coolify 4.0.0-beta.469 the run pauses for one dashboard step, because that version cannot create a storage through its API. `--rollback` and `--cleanup` keep the volume. Without the flag, a volume still blocks the move.
- `hatchkit migrate-runtime --same-json <service>=/path:<field>` compares one JSON field between production and the new app before any traffic moves. A difference stops the run with the compose app serving.
- `hatchkit doctor` warns for every app of the project whose deploys still take the site down, and names the command that fixes it.
- `hatchkit config pause <provider> --reason "<why>" [--since YYYY-MM-DD]` marks a provider you stopped on purpose, such as a self-hosted GlitchTip. `hatchkit doctor` then shows it as skipped with the reason and date instead of failing on its 503. `hatchkit config resume <provider>` checks it again. The credentials stay stored.

### Fixed

- `hatchkit email status` and `hatchkit email forward` read a verified forwarding inbox as verified. Cloudflare reports a destination's verification as a timestamp, not the word "active" that hatchkit compared against, so every verified inbox showed as pending and `email forward` refused with "No rule created".
- `hatchkit email setup` for a hostname below its zone (`app.example.com`) now registers the hostname with Email Routing. Before, it wrote MX, SPF and DMARC records that Cloudflare ignored, because Cloudflare receives only for names it lists under the zone's subdomains, so mail to the new addresses bounced. The run ledger records the registration, and `hatchkit destroy` removes it. `email status` shows it on a `Subdomain:` line. Setup also leaves the MX records Email Routing locked, and an SPF record that differs only by quotes, as they are.
- `hatchkit email setup` records the forwarding it set up in `.hatchkit.json`, as `hatchkit add <project> email` already did. doctor, the Cloudflare audit and `migrate-domain` read it from there.
- `hatchkit update --dry-run` now describes the operational layer (verified deploy, deploy recovery, error reporting and the rest). It returned before the layer ran, so a dry run that listed nothing was followed by a real run that wrote those files.
- Client error reporting is written into the project's own client, the same one deploy recovery uses, instead of always into `packages/client/src/lib/error-reporting`. A single-package site gets it beside its `app/`. A repository whose root package is a CLI or a library, with its web app in `docs/`, `site/` or `website/`, gets it there, and the browser SDK goes into that package's dependencies.
- The operational layer now reads `deploymentMode` and `clientRelease`. A site not deployed to Coolify (`cloudflare`, `gh-pages`, `scaffold-only`) gets no verified-deploy scripts or rollback workflow, no topology write-up and no docs build step for a client image, because it has no Coolify app and no image. A site with `clientRelease: "repo"` gets no deploy-recovery code, because its own release workflow already decides how an open tab learns of a deploy.
- The docs-in-client module no longer writes into `packages/client/` when the project has none. Its paths only exist in the starter's layout, so another layout is left alone, as its own documentation already said.
- Error reporting leaves a reporter the project wrote itself alone. hatchkit's generated files say so in their headers, so a directory where none does was never generated; `--force` still replaces it. The generated scrubber also removes local file paths from error messages (`/Users/…`, `/home/…`, `file://…`, `C:\…`, `\\share\…`), file name included, because an app that opens the user's files names them in its errors. Stack frames keep their paths.
- `hatchkit doctor` no longer fails on Plausible Community Edition, which never serves the Sites API. It checks `/api/health` and, inside a project, the Stats API for the project's domain, and warns only when the Stats API refuses that domain.
- doctor's Cloudflare Workers provisioner row probes the zone grants on the zone of the project's domain, names the zone it probed, and prints each failing probe's error. A denied grant and a probe that got no answer are reported apart.
- A provider check whose request failed in the network now names the reason, for example `fetch failed (ECONNRESET)`, instead of `fetch failed` alone.
- "Coolify GitHub App (sources)" with no sources is a skip, not a failure: only `hatchkit create --private` needs one.
- An Email Routing permission error names the call Cloudflare refused and the one permission it needs. Reading a zone's routing settings needs Zone → Zone Settings → Read (Edit to enable routing), not Email Routing Rules, which the hint used to ask for.
- Manifest migration notes print once per run, with the command that writes the migrated file (`hatchkit update`). doctor used to print them once per manifest read.
- `npm install hatchkit` works again with the next release. hatchkit 0.2.16 to 0.2.19 on npm list `@hatchkit/dev-shared` as `workspace:*`, and npm rejects that with `EUNSUPPORTEDPROTOCOL`. The release published the CLI with `npm publish`, which keeps `workspace:*`. It now uses `pnpm publish`, which writes the real version.
- `pnpm release` (maintainers) now finishes with an npm account that requires 2FA to publish. Each publish runs in the terminal, so npm can show its "Authenticate your account" prompt instead of failing with `EOTP`. Every package is published before the commit and tag are pushed. A version already on npm is skipped, so `pnpm release:resume` finishes a release that stopped, and a new `pnpm release` on top of one refuses to bump past it.
- The release tag is now annotated and pushed with the version commit. `git push --follow-tags` skipped the lightweight tag, so v0.2.19 reached GitHub only by hand.
- The release also runs where `pnpm` is not on PATH, for example a shell on Homebrew's Node, which ships no corepack. Nested `pnpm` calls use the pnpm that started the release. With no pnpm at all, it stops before the version bump.

### Removed

- **OpenPanel support is gone.** Plausible covers web analytics and GlitchTip covers errors. Hatchkit no longer configures OpenPanel (`hatchkit config add openpanel`), provisions or removes OpenPanel projects (`hatchkit add|remove <project> openpanel`), rotates OpenPanel clients (`hatchkit secrets rotate --providers=openpanel`), or checks OpenPanel in `status`, `doctor`, `overview` and `inventory`. `openpanel` is no longer a valid `--analytics-providers` or `--services` value. New projects no longer get the `op.js` script tag, the `@openpanel/nextjs` dependency, or the `NEXT_PUBLIC_OPENPANEL_CLIENT_ID` / `OPENPANEL_*` env and build-arg entries. Existing setups keep working: a CLI config with a `providers.openpanel` block loads and the block is ignored (`hatchkit config reset` clears it and its keychain entries), a manifest's `service:openpanel` deferral is dropped, and a run ledger's OpenPanel step prints a manual-cleanup hint on `destroy`. Nothing is removed from existing projects; delete their OpenPanel env vars and script tag by hand.

- **`desktop-tauri` is gone.** Electron is the one desktop wrapper. Both wrapped the same static client export, so a second release pipeline bought nothing. Removed: `starter/src-tauri/`, `tauri-release.yml`, the four `tauri`/`icons:tauri` scripts, `@tauri-apps/cli`, the `tauri://localhost` + `http://tauri.localhost` trusted origins, and the `--features desktop-tauri` value. `hatchkit signing`'s `windows` platform now detects `electron/` instead of `src-tauri/` and its `build-windows.yml` builds an electron-builder NSIS installer signed with Azure Trusted Signing. An existing `.hatchkit.json` that lists `desktop-tauri` is migrated on read (manifest v5): the flag is dropped with a note, nothing is deleted from the project, and an already-deployed server keeps trusting the origins it already trusts — `TRUSTED_ORIGINS` is merge-only. A project that still wants Tauri should pin an older CLI or keep its `src-tauri/` tree by hand.
- The starter's `itch:push:{mac,win,linux}` scripts and the itch.io/butler steps in `desktop-release.yml`. The workflow now uploads each platform's installer as a build artifact; attach them to a release, or add a distribution step of your own.

### Added

- **SES bounces and complaints reach Listmonk for every new identity.** `hatchkit add <project> listmonk-ses` and `hatchkit migrate-domain` created the SES identity with DKIM and MAIL FROM but set no notification topics, so its bounces went only to `noreply@` and Listmonk never blocklisted a dead address. Both now point the identity's Bounce and Complaint notifications at the shared `ses-feedback-listmonk` SNS topic, subscribe that topic to `<listmonk-url>/webhooks/service/ses`, add `BOUNCE` and `COMPLAINT` to the account suppression list, and turn on Listmonk's `bounce.enabled`, `bounce.webhooks_enabled` and `bounce.ses_enabled`. Each piece is read first and written only when missing, so a re-run makes no writes and Listmonk reloads only for a setting that changed. `hatchkit destroy <project>` clears only the notification topics that project set; the shared topic, subscription, suppression and Listmonk settings stay. The IAM user needs seven more actions (listed in the email docs); without them provisioning warns and continues.
- `hatchkit doctor` checks the SES bounce feedback path across the account: verified identities without Bounce/Complaint topics, a missing or unconfirmed subscription, account suppression, and Listmonk's bounce settings. `hatchkit doctor --fix` repairs each one.
- `hatchkit doctor --fix`: after the report, doctor offers the repairs it can apply itself, one `y/N` prompt each (default No; `--yes` applies them all). The first one pipes an escaped tx template's body through `Safe`. It reads the template again before the write and changes only the bare `{{ .Tx.Data.body }}` actions. Plain `doctor` and `doctor --json` stay read-only.
- **Scaffold-time identifier resolution** (`cli/src/scaffold/identifiers.ts`). Bundle id, product name, home-screen short name, storage and secret-store prefixes, the client and webhook header names, per-surface device-flow client ids, database name, export filename prefix, env-var prefix, npm scope and the desktop origin are now decided **once**, validated against the rules each platform actually enforces, and recorded in the manifest's new `identifiers` block (schema v5) — instead of being re-derived at five call sites under three different rules. `hatchkit signing` takes its bundle-id and app-name defaults from that block rather than computing its own, so the two can no longer disagree. Product name and short name are separate decisions from the project slug: `name` is what npm and the image registry use, `productName` is what a person reads, and `shortName` is the launcher label, which elides past about twelve characters. Organisation prefix defaults to the deliberately obvious `com.example` and `hatchkit create` warns while it is still there — an App ID, an App Store Connect record and a Play package name cannot be renamed once registered.
- **Cross-file identifier agreement check** (`cli/src/scaffold/identifier-agreement.ts`). The bundle id and the launcher label each live in up to four files that no single tool owns — `package.json`'s electron-builder block, `capacitor.config.ts`, the web app manifest, and the committed iOS and Android trees `cap add` generates. Every copy present is now read back and compared with the manifest, and a disagreement is reported with the file, the field and both values. A drifted copy previously surfaced as a store upload rejected days later with a message that named no file.
- The starter's web app manifest, which was an empty `{}` that nothing wrote, now carries the product and short names.
- `docs/feature-authoring.md` — the contract for adding an opt-in feature: registration, prerequisites, editing a file the user also edits without clobbering it, `--dry-run`, and what to test. Backed by a shared mechanism in `cli/src/features/contract.ts` (a feature registry with enforced `requires`, and a ledger that is the single `--dry-run` choke point and the only safe way to write) and `cli/src/features/templates.ts`.
- `docs/template-gaps.md` — 303 rows covering every gap between the starter template and a reference project taken to production, grouped by the twelve follow-up features, each with the invariant that fails quietly if it is done wrong.

- New `desktop-tauri` feature: a Tauri-based desktop wrapper aimed at games — much smaller binaries than Electron, plus Steamworks integration on the Rust side behind an opt-in `steam` cargo feature (`pnpm tauri build -- --features steam`). `hatchkit create` offers it after the feature checkbox whenever `mobile` (Capacitor) is selected and the Electron wrapper isn't; `hatchkit update` adds it to existing projects (idempotent on re-run). The starter ships `src-tauri/` (config, crate, capabilities, icons, entitlements) and a `tauri-release.yml` CI workflow with signed + notarized macOS builds and Azure Trusted Signing on Windows, both gated on the corresponding secrets. The two desktop wrappers are mutually exclusive — selecting both `desktop` and `desktop-tauri` is rejected with "pick one desktop wrapper".
- Added GitHub community health files, issue templates, release-note config, Dependabot config, and package metadata so the repository is easier to evaluate and contribute to.
- `hatchkit add <project> listmonk-ses` now auto-subscribes the user's configured forwarding email onto the project's `-test` Listmonk list as `confirmed`, and writes the address into `.env.development` as `LISTMONK_TEST_RECIPIENT`. Skipped silently when no default forwarding email is on file.
- Starter ships bundled smoke scripts: `pnpm newsletter:test-tx`, `pnpm newsletter:welcome`, and `pnpm newsletter:verify` — each defaults to `LISTMONK_TEST_RECIPIENT` so a fresh provision is one command away from a real send in your own inbox. Verify runs four checks (API reach, list ids, subscriber state, real tx send) and exits non-zero on the first failure.
- Starter ships pre-built example email HTML at `emails/welcome.html` and `emails/digest-sample.html`. Edit them; `pnpm newsletter:welcome` reads `welcome.html` and `pnpm newsletter:draft emails/digest-sample.html --subject "Issue 1"` stages the digest as a Listmonk draft.

### Changed

- Listmonk + SES is now the only supported email path. The opinionated email intent maps both transactional and newsletter needs to `listmonk-ses`; the starter ships a Listmonk `/api/tx` sender (with the matching `LISTMONK_*` env keys) in place of the Resend HTTP client.

### Fixed

- `hatchkit migrate-runtime` resolves `${VAR:?message}` and `${VAR:+value}` in a compose file the way Compose does. Before, it copied the text `${VAR:?message}` to the new app as the variable's value. A required variable that is not set on the app now blocks the move.
- **`hatchkit add <project> listmonk-ses` no longer takes over the shared Listmonk's default sender.** Each time it wrote the SMTP settings, it also set Listmonk's `app.from_email` to `<project-slug> <noreply@mail.<domain>>`. That setting is instance-wide, and one Listmonk serves every project, so provisioning one project made it every other project's default sender. It now sets `app.from_email` only when it is empty or still Listmonk's install default, and leaves any other value alone. Apps built from the starter are not affected either way: they pass `LISTMONK_FROM` on every send.
- **`hatchkit add <project> listmonk-ses` no longer writes masked secrets into Listmonk.** It read `GET /api/settings` and wrote the whole document back with `PUT /api/settings`. GET masks every secret as a row of `•`, so the PUT could write the masks over the bounce-mailbox passwords and the S3 and OIDC secrets, and it dropped every SMTP server except SES. The SMTP relay now goes through the per-key `PUT /api/settings/smtp` (Listmonk v6), and the SES server keeps its name, UUID and tuning. If the SMTP list holds another server with a password, `add` does not write it and prints the manual steps. The masked password also made the "already in place" check fail on every run, so every run rewrote the settings and reloaded Listmonk. The check now compares host, port, username and the password's length, and a re-run with the same IAM key writes nothing.
- **`hatchkit migrate-domain` no longer takes over the shared Listmonk's default sender.** The cutover step wrote `<project-slug> <noreply@mail.<new>>` into Listmonk's `app.from_email`. That setting is instance-wide, and one Listmonk serves every project, so each migration made the migrated project every other project's default sender. The step now reads `app.from_email` and rewrites it only when it sends from this project's old identity. It swaps only the domain, so the display name and local part stay. Any other value is left alone. The write uses the per-key `PUT /api/settings/app.from_email` (Listmonk v6), not the whole-document PUT. Apps built from the starter are not affected either way: they pass `LISTMONK_FROM` on every send, and the SES cutover moves it.
- **A migrated SES identity keeps its bounce and complaint routing.** `hatchkit migrate-domain` now copies the old identity's Bounce and Complaint SNS topics onto the new identity in the prepare phase, then checks them again at cutover, before the new identity sends. The shared `ses-feedback-listmonk` topic gets only the types the old identity did not route. If the IAM user may not call `ses:SetIdentityNotificationTopic`, the step does not fail. It prints the exact `aws ses set-identity-notification-topic` commands and records them under `deferred[]`. `hatchkit add <project> listmonk-ses` prints the same commands in that case.
- **Newsletter signups are real double opt-in.** `hatchkit add <project> listmonk-ses` created the Listmonk lists `optin: single`, and the starter's subscribe form added each address to the list as `unconfirmed` before the confirmation link was clicked. Listmonk sends a campaign on a single-opt-in list to every member not `unsubscribed`, so an address that never confirmed still got every campaign. New lists are now `optin: double`. The starter's form now creates the subscriber on no list (`ensureSubscriber`), and only the confirm link adds the list, as `confirmed` (`confirmSubscription`). With that order, Listmonk never sends its own opt-in email next to the app's. `upsertSubscriber` is gone; `newsletter:test-tx` and `newsletter:welcome` no longer add the recipient to a list. Existing lists are not switched: `add` on an adopted single-opt-in list and `hatchkit doctor` in the project report it, with the order to fix it in (deploy the confirm-only code first, then switch the list).
- The starter's and the CLI's Listmonk subscriber lookup used the `query` parameter, which needs the `subscribers:sql_query` permission that Listmonk's role form leaves out by default. Both now use an anchored `search` with regex characters quoted, so a plus-address such as `a+b@example.com` matches itself, and keep only the exact email from the results.
- Native clients (`mobile`, `desktop`, `desktop-tauri`) no longer fail sign-in with `403 INVALID_ORIGIN` on projects whose production env lives in Coolify. `hatchkit create`, `adopt`, `update` (after adding a native feature) and `sync` merge the shells' origins into `TRUSTED_ORIGINS` on the server Coolify app. Existing entries are kept in order and nothing is removed. The diff is confirmed before the write (`--yes` skips the prompt, `--dry-run` stops after the diff) and read back after it. `sync --deploy` redeploys the server; other paths print that a redeploy is needed. `sync`'s env pass now merges a `.env.production` `TRUSTED_ORIGINS` into the live value instead of overwriting it. The deploy workflow gains a "Verify native clients can sign in" step that probes each origin with `Sec-Fetch-Mode: cors` and fails on `403 INVALID_ORIGIN`.
- **Transactional emails no longer arrive as visible HTML markup.** `hatchkit add <project> listmonk-ses` seeded the `<project>-tx` template with a body of `{{ .Tx.Data.body }}`. Listmonk parses a tx template body with Go `html/template` (only the subject uses `text/template`), so that body HTML-escaped every confirmation and reset email. The seeded body is now `{{ .Tx.Data.body | Safe }}`; `Safe` is the helper Listmonk registers for tx templates (`safeHTML`, the earlier attempt, is not registered and fails to compile). `hatchkit doctor`, run in a project directory, reports a `<project>-tx` template that still has the bare body.
- `fix(dns): preserve Cloudflare API token across legacy-provider auto-migration` — `ensureDns` no longer wipes `dns:cloudflare:token` when migrating a pre-v2 `inwx`/`manual` DNS config. The token is read first, verified against `GET /user/tokens/verify`, and reused under the new `provider: "cloudflare"` meta so users keep their existing token instead of being forced to roll + re-paste (Cloudflare never re-exposes token values). Only the `dns:inwx:password` secret and the stale `provider` field are cleared. Explicit `hatchkit config add dns` still wipes both — that path is user-initiated.

### Removed

- Removed the Resend provider, configure flow, provision/destroy paths, and all `--resend-*` flags from `hatchkit add`. The starter's email service and `better-auth` reset/verify hooks now talk to Listmonk + SES; existing projects keep working until their next provisioning run.
