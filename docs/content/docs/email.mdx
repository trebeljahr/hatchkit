---
title: Email — Listmonk + SES
description: Self-hosted mailing-list manager backed by AWS SES delivery. The sovereign-cheap alternative to Resend Pro for transactional sends and broadcasts.
---

Hatchkit can wire up two providers for outbound email:

| Need | Resend | Listmonk + SES |
|---|---|---|
| Transactional sends | one API key per env | Listmonk `/api/tx` |
| Mailing list broadcasts | Audiences | Listmonk lists |
| Subscribe / confirm / unsub UI | bring your own | Listmonk admin UI |
| Cost (low-volume hobbyist) | €20/month entry tier | ~€0.10 per 1,000 sends + €0 Listmonk |
| Owns IP reputation | Resend | you (via SES) |
| Setup friction | one paste of an API key | SES + Listmonk + admin wizard |

If you only need transactional sends and don't want to think about infra, Resend is the right answer. If you run more than one project from your domain, or you want a sovereign + cheap stack, Listmonk + SES is the pick.

## How the stack composes

```text
                                  ┌─ Listmonk API ──┐
your app  ─── HTTPS POST ─────────┤                 │── Listmonk UI: lists, subscribers,
          /api/subscribers       │                 │   broadcasts, bounces
          /api/tx (transactional)│                 │
                                  └──────────┬──────┘
                                             │ SMTP
                                             ▼
                                      AWS SES (email-smtp.<region>.amazonaws.com)
                                      DKIM-signs + delivers
```

- SES owns IP reputation, delivery, bounce + complaint feedback.
- Listmonk owns subscribe/confirm/broadcast/template UX.
- The app talks to Listmonk only: `LISTMONK_URL` + `LISTMONK_API_USER` + `LISTMONK_API_TOKEN` + `LISTMONK_LIVE_LIST_ID` (production) or `LISTMONK_TEST_LIST_ID` (everywhere else) for list operations and `/api/tx` transactional sends. `SES_FROM_EMAIL` and `SES_REGION` name the sending identity.
- Each project has its own Listmonk API user (see [One API user per project](#one-api-user-per-project)).
- The SES SMTP login stays in Listmonk's settings, not in the app's env. Nothing in the starter sends SMTP itself. The SMTP password derives from hatchkit's own SES IAM secret, so it carries that IAM user's rights, not the project's.

## One-time global setup

### 1. AWS SES

```sh
hatchkit config add ses
```

You'll be prompted for an AWS region (suggest `eu-west-1` for EU compliance) and an IAM access key id + secret. The credentials need these IAM actions (SES API v1 and v2 both use the `ses:` prefix):

- `ses:CreateEmailIdentity`, `ses:GetEmailIdentity`, `ses:ListEmailIdentities`, `ses:DeleteEmailIdentity`
- `ses:PutEmailIdentityMailFromAttributes` (custom MAIL FROM)
- `ses:SendEmail` / `ses:SendRawEmail`
- For [bounces and complaints](#bounces-and-complaints):
  - `ses:SetIdentityNotificationTopic`, `ses:GetIdentityNotificationAttributes`
  - `ses:GetAccount`, `ses:PutAccountSuppressionAttributes`
  - `sns:CreateTopic`, `sns:Subscribe`, `sns:ListSubscriptionsByTopic`, `sns:Unsubscribe`

`AmazonSesFullAccess` does not cover the four `sns:` actions. For least privilege, copy the actions above into a custom policy. When one is missing, provisioning prints a warning that names it and continues, and `hatchkit doctor` reports the check it could not run.

**SES sandbox mode is the default.** New AWS accounts can only send to recipient addresses verified ahead of time. To send to real users you must request production access via the AWS console (one-time form, ~24h Amazon review).

While sandboxed, register every test recipient with:

```sh
hatchkit ses verify <email>
```

A send to an unverified recipient fails without any sign in your app: Listmonk's `/api/tx` returns 200 before SMTP runs, and the SES rejection shows only in Listmonk's log (`GET /api/logs`).

SES mails a one-time confirm link to that address; clicking it flips it to verified. Drop one with `hatchkit ses unverify <email>`. See the current account state (sandbox flag + send caps + identity count) with:

```sh
hatchkit ses status
```

Hatchkit verifies your project's *sending* domain + derives SMTP creds before sandbox lifts; only actual broadcasts to non-verified recipients are blocked.

### 2. Listmonk

You need a running Listmonk instance somewhere. If you already self-host one:

```sh
hatchkit config add listmonk
```

If you don't yet have one and want it on your Coolify install:

```sh
hatchkit config add listmonk --deploy
```

The `--deploy` flag prints a step-by-step walkthrough for the Coolify Listmonk service template. It is deliberately a guided manual flow — Coolify's services-from-template endpoint shape drifted across v4.x minor versions, and the next two steps after deployment are unavoidably manual anyway:

1. **Open the Listmonk URL** Coolify auto-assigns. Complete the first-boot wizard — pick a superadmin username + password.
2. **Admin → Users → New API user.** Name it `hatchkit`. Required permissions on the role:
   - `Lists: All` — hatchkit creates per-project lists.
   - `Subscribers: All` — signup forms add subscribers.
   - `Campaigns: All` — transactional sends via `/api/tx`.
   - `Settings: All` — so hatchkit can push SES SMTP creds into Settings → SMTP without manual paste.
   
   Skipping `Settings: All` is OK — provisioning still works, but the SES SMTP step falls back to manual paste in the Listmonk admin UI. Copy the generated token after save.

Then hatchkit prompts you for the URL + API user name + token. It validates by hitting `GET /api/lists` before storing anything.

3. **Admin → Users → New API user** again, for the admin credential: name `hatchkit-admin`, role `Super Admin`. Hatchkit uses it to create each project's own role pair and API user. The `hatchkit` user above has no `users:*` or `roles:*` permission, and it should not get them. Store the token in the keychain only; the command prompts for it, so the token stays out of your shell history:

   ```sh
   security add-generic-password -U -s hatchkit -a listmonk:admin-api-token -w   # macOS
   secret-tool store --label="hatchkit listmonk:admin-api-token" service hatchkit account listmonk:admin-api-token   # Linux
   ```

   Without it, every project gets the `hatchkit` user and its token, and provisioning prints a warning.

### 3. Wire SES into Listmonk's SMTP settings

Listmonk delivers via SMTP, so the SES SMTP relay credentials need to land in **Listmonk's** Settings → SMTP. `hatchkit add <project> listmonk-ses` writes them with Listmonk's per-key `PUT /api/settings/smtp` (Listmonk v6 or later), provided the API user's role includes `Settings: All`. If it does, you'll see:

```
✓ Listmonk SMTP settings auto-configured to SES.
```

The write happens only when the host, port, username or password differ: on the first run, or after the SES IAM key rotates. An existing SES server keeps its name and tuning. Listmonk reloads by itself after the write. If a campaign is running, Listmonk saves the settings but does not reload, and hatchkit tells you to restart it after the campaign.

Hatchkit never uses the whole-document `PUT /api/settings`. `GET /api/settings` masks every secret (SMTP and bounce-mailbox passwords, the S3 and OIDC secrets), and a whole-document PUT would write the masks back. For the same reason, hatchkit will not rewrite the SMTP list when it holds another server with a password: the per-key write replaces the whole list, and that server's password is unknown. It prints a warning, and you add the SES server by hand.

One Listmonk serves every project, so its default sender (Settings → General → Default 'from' email, `app.from_email`) belongs to no single project. It sends Listmonk's own mail, such as opt-in confirmations, and any campaign or tx call that names no sender. Apps built from the starter pass `LISTMONK_FROM` on every call, so they do not depend on it. Hatchkit sets it only when it is empty or still Listmonk's install default (`listmonk <noreply@listmonk.yoursite.com>`). Any other value is left alone.

If the API user lacks `Settings: All`, hatchkit downgrades to a warning and you paste manually. Print the values with:

```sh
hatchkit ses smtp --show-password
```

Listmonk → Settings → SMTP → enable, paste host, port, username and password, save. Auth protocol: `LOGIN`. TLS type: `STARTTLS`. If Settings → General → Default 'from' email is empty, set it to `noreply@mail.<projectDomain>`.

## Per-project provisioning

```sh
hatchkit add <project> listmonk-ses
```

This runs these steps, all idempotent on re-run:

1. **Verify the SES sending subdomain.** Hatchkit calls `CreateEmailIdentity` for `mail.<projectDomain>` and gets back 3 DKIM tokens.
2. **Publish DKIM CNAMEs into Cloudflare.** Same upsert + SPF-merge plumbing as Resend's flow. Records are tracked in the run-ledger so `hatchkit destroy <project>` can DELETE only what this run created.
3. **Route bounces and complaints to Listmonk.** The identity's Bounce and Complaint notifications go to the shared SNS topic that Listmonk listens on. See [Bounces and complaints](#bounces-and-complaints).
4. **Create the project's Listmonk lists.** `<project>` (live, its id lands in `.env.production`) and `<project>-test` (dev, its id lands in both env files). Both are private and double opt-in (see [Double opt-in](#double-opt-in)). A list that already exists by that name is reused as it is. If it is still single opt-in, the run reports it and leaves it unchanged.
5. **Create the project's own Listmonk API user.** A user role, a list role and an API user, each named `<project>`. See [One API user per project](#one-api-user-per-project).
6. **Render env into the server bundle.** `LISTMONK_*` plus `SES_FROM_EMAIL` and `SES_REGION`. `LISTMONK_API_USER` and `LISTMONK_API_TOKEN` name the project's own user. Both files get `LISTMONK_TEST_LIST_ID`. Only `.env.production` gets the live list's id, as `LISTMONK_LIVE_LIST_ID`, so code run against the development env cannot pick the live list by its id. The development values, including the API token, go to the gitignored `.env.development.local`, not the committed `.env.development`. The starter reads the live id only when `NODE_ENV=production`. Env files written by an older Hatchkit hold the live id as `LISTMONK_LIST_ID`; the starter still reads that name in production when `LISTMONK_LIVE_LIST_ID` is unset.

SES verification flips from Pending → Verified once DNS propagates (usually under 30 min). Hatchkit doesn't poll for it — you can check status anytime with `aws sesv2 get-email-identity --email-identity mail.<projectDomain>`.

## One API user per project

One Listmonk serves every project. If every project held the same token, a leak from any one app would carry that token's rights on the whole instance. So each project gets its own objects, all named after the project:

| Object | Grants |
|---|---|
| User role `<project>` | `tx:send`, `subscribers:get_all`, `subscribers:manage`, `campaigns:manage` |
| List role `<project>` | `list:get` + `list:manage` on the `<project>` and `<project>-test` lists |
| API user `<project>` | both roles |

The role needs `subscribers:get_all`, not `subscribers:get`. The signup form creates each subscriber on no list until the confirm click (see [Double opt-in](#double-opt-in)). With `subscribers:get` alone, Listmonk limits subscriber queries to the user's own lists. The confirm step then cannot find the address, and creating it again fails with a 409. The cost: the token can read every subscriber on the instance. Listmonk also cannot limit a user to its own templates or senders.

The project token cannot read or change Listmonk's settings: `GET /api/settings` answers 403.

Listmonk shows an API user's token once, when it creates the user. Hatchkit keeps it in the keychain (`listmonk:project:<project>:api-token`) and in the project's env files. A second run finds all three objects by name and reuses the token. If the user exists but no stored token works, hatchkit stops. Listmonk cannot regenerate a token, so the only fix is to delete the user and create it again, and that breaks the deployed copy of the old token. Hatchkit does it only after a yes at the prompt, or with `--regenerate-token` (`--regenerate-listmonk-token` on `hatchkit add`). Hatchkit never updates an existing API user in place: on Listmonk v4.0 to v6.1, that sets its token to NULL.

A role that lacks one of the permissions or lists above gets it added. Anything else the role holds stays.

### Existing projects

Projects provisioned before this change hold the `hatchkit` user and its token. Move one to its own user with:

```sh
hatchkit listmonk user <project> --dry-run   # print the plan
hatchkit listmonk user <project>
```

It reads the list ids from the project's env (`LISTMONK_LIVE_LIST_ID`, or `LISTMONK_LIST_ID` in older files, and `LISTMONK_TEST_LIST_ID`), or finds the lists by name. It creates the three objects and writes `LISTMONK_API_USER` + `LISTMONK_API_TOKEN` into `.env.production` (encrypted). If the development env uses Listmonk, it writes them into `.env.development.local` too. It also removes `SES_SMTP_*` lines when no file in the project's git tree reads them; `--keep-ses-smtp` leaves them.

It does not push to Coolify. Run `hatchkit sync` and redeploy. Sync only adds and updates variables, so delete `SES_SMTP_*` from the Coolify app's environment by hand. When no project holds the `hatchkit` token any more, retire it with `hatchkit secrets rotate --global listmonk`.

## Double opt-in

The starter's signup form runs its own double opt-in: it emails an HMAC-signed confirmation link through Listmonk's `/api/tx`. Listmonk list membership follows this order:

1. **Form submit.** The server makes sure the address exists as a Listmonk subscriber, on **no** list. `/api/tx` needs only that. An address Listmonk already knows is left as it is: it may be on another project's list, or `unsubscribed` from this one.
2. **Confirm click.** The server adds the list with `PUT /api/subscribers/lists`, `action: "add"`, `status: "confirmed"`. A subscriber deleted in the meantime is created again with `preconfirm_subscriptions: true`.

The lists are `optin: double`, so a campaign reaches `confirmed` members only. Two Listmonk behaviours make the order matter:

- On a **single** opt-in list, Listmonk sends a campaign to every member not `unsubscribed`, `unconfirmed` included. An address added before the click would get every campaign without confirming.
- On a **double** opt-in list, Listmonk sends its own opt-in email whenever a subscriber is created or updated with `preconfirm_subscriptions: false` and has an `unconfirmed` membership on that list (with `app.send_optin_confirmation` on, the default). An address added before the click would get two confirmation emails.

Lists that `hatchkit add` created before this change are single opt-in. `hatchkit doctor`, run in the project directory, reports them. Switch one only after the app that writes to it runs the confirm-only code, then set **Listmonk → Lists → edit → Opt-in: Double**.

The confirmation link points at the API's origin, `BETTER_AUTH_URL`. The confirm route then redirects to `/sub/confirmed` or `/sub/error` on the site's origin, `NEWSLETTER_SITE_URL` (else `FRONTEND_URL`). Under the `split` topology these are two hosts, and only the API host serves `/api/newsletter/confirm`. Projects created before 2026-09-29 built the link on the site's origin, so under `split` it returned a 404. `hatchkit update` moves the link to `BETTER_AUTH_URL`.

## Tearing down

```sh
hatchkit remove <project> listmonk-ses
```

Removes the per-project Listmonk lists. With the `hatchkit-admin` credential, it also deletes the project's API user, then its user role, then its list role. A role another user still holds stays. The SES identity (`mail.<projectDomain>`) is intentionally left in place because un-verifying it requires re-publishing DKIM if you ever recreate the project. To fully destroy SES state, use `hatchkit destroy <project>` — the ledger-driven destroy honors the `sesDomain` step. It also clears the identity's Bounce and Complaint notification topics, but only the ones that run set. The shared SNS topic, its subscription, the account suppression list and Listmonk's bounce settings stay, because the other projects use them.

## Bounces and complaints

Every project sends through the same Listmonk, so they share one feedback path:

```text
SES identity ── Bounce / Complaint ──▶ SNS topic ses-feedback-listmonk
                                         │ HTTPS subscription
                                         ▼
                        <listmonk-url>/webhooks/service/ses ──▶ Listmonk blocklist
```

`hatchkit add <project> listmonk-ses` and `hatchkit migrate-domain` (for the new identity) set up each piece that is missing:

1. **Listmonk bounce settings.** `bounce.enabled`, `bounce.webhooks_enabled` and `bounce.ses_enabled` are set to `true`, one `PUT /api/settings/<key>` each. A key that is already `true` is not written, because each PUT reloads Listmonk. The per-key endpoint needs Listmonk v6 and an API user with `Settings: All`.
2. **SNS topic and subscription.** The topic is `ses-feedback-listmonk`, in the SES region. Its HTTPS subscription points at the webhook derived from the Listmonk URL you stored with `hatchkit config add listmonk`, with basic-auth credentials in the URL (see [Basic auth on the SNS endpoint](#basic-auth-on-the-sns-endpoint)). Listmonk confirms the subscription by itself once `bounce.ses_enabled` is on, so the URL must be reachable from AWS.
3. **Identity notifications.** The identity's Bounce and Complaint topics are set to the shared topic. This is the SES v1 `SetIdentityNotificationTopic` call; SES v2 routes notifications through configuration sets instead. A topic already set on the identity to a different SNS topic is left alone and reported. `hatchkit migrate-domain` first copies the old identity's Bounce and Complaint topics onto the new identity, so the new identity reports to the same place as the old one. The shared topic gets only the types the old identity did not route. The cutover phase checks the topics again before the new identity starts sending. If the IAM user may not call `SetIdentityNotificationTopic`, the run prints the exact `aws ses set-identity-notification-topic` command for each type. `migrate-domain` also records them in `.hatchkit.json` under `deferred[]`.
4. **Account suppression.** SES suppresses `BOUNCE` and `COMPLAINT` addresses account-wide, so it stops sending to them.

What Listmonk does with a bounce is set in **Settings → Bounces → Actions**. Hatchkit does not change it. Blocklisting after one hard bounce and after one complaint keeps the SES bounce and complaint rates low.

Without step 3, SES only emails a bounce notice to the sender address (`noreply@mail.<projectDomain>`), which nobody reads, and Listmonk keeps sending to the dead address.

`hatchkit doctor` checks the whole path wherever SES and Listmonk are configured. It reports every verified identity without Bounce or Complaint topics, a missing or unconfirmed subscription, a second subscription of the same webhook, suppression that doesn't cover both reasons, and Listmonk bounce settings that are off. `hatchkit doctor --fix` repairs each one after a `y/N` prompt.

### Basic auth on the SNS endpoint

SNS supports HTTP basic auth for HTTPS endpoints. Hatchkit generates a user and a password once, stores them in the keychain (`ses:feedback-webhook:user`, `ses:feedback-webhook:password`), and subscribes `https://<user>:<password>@<listmonk-host>/webhooks/service/ses`. Without a proxy that checks them, Listmonk takes the request as before. Output shows the endpoint with the password as `****`.

Once the credentialed subscription is confirmed, hatchkit removes an older subscription of the same webhook, such as the plain one from an earlier version. Otherwise SNS would deliver each notification twice. If the IAM user may not call `sns:Unsubscribe`, the run prints the `aws sns unsubscribe` command.

To require the credentials, put a basic-auth router in front of `/webhooks/service`. For Listmonk behind Traefik (Coolify, for example):

```sh
hatchkit ses webhook-auth --service <listmonk-traefik-service>
```

It prints labels for one router per entry point on `Host(<listmonk-host>) && PathPrefix(/webhooks/service)`, with priority 1000 and a `basicAuth` middleware that holds a bcrypt hash of the password. The password itself is never printed. `--service` is the service in Listmonk's own `traefik.http.services.<name>.loadbalancer.server.port` label. `--cert-resolver` defaults to `letsencrypt`. `$` is doubled for a compose file; pass `--no-compose-escape` for a plain list. Add the labels to the Listmonk container, redeploy, and check that `/webhooks/service/ses` answers `401` without credentials.

The credentials belong to one machine's keychain. A run on a machine without them generates new ones, and its subscription stays pending until the proxy has their hash.

## Troubleshooting

**`CreateEmailIdentity` fails with `AccessDeniedException`** — the IAM user needs the policy listed above. Re-run `hatchkit config add ses` to repaste a key with the right policy attached.

**Listmonk says `unauthorized`** — your API user's permissions are too narrow. Edit them in Admin → Users; grant Lists / Subscribers / TX. Then re-run `hatchkit config add listmonk` to repaste the (still-valid) token. The `subscribers:sql_query` permission is not needed: subscriber lookups use `search`.

**The email arrives, but shows HTML tags as text** — the project's `<project>-tx` template renders a bare `{{ .Tx.Data.body }}`. Listmonk parses a tx template body with Go `html/template`, which escapes the app's HTML. Hatchkit seeded this body in earlier versions. `hatchkit doctor`, run in the project directory, reports it, and `hatchkit doctor --fix` changes it to `{{ .Tx.Data.body | Safe }}`. You can also make that edit in **Listmonk → Campaigns → Templates**.

**Send fails: `Email address is not verified`** — your SES account is still in sandbox mode. Request production access in the AWS console.

**The form says "check your inbox", but no confirmation email arrives** — usually the SES sandbox. `/api/tx` queues the email and returns 200 before SMTP runs, so the app reports success either way. The SES rejection (`554 Message rejected: Email address is not verified`) shows only in Listmonk's log: **Settings → Logs**, or `GET /api/logs`. Verify the recipient with `hatchkit ses verify <email>`, or request production access.

**Provisioning warns `missing IAM permission sns:CreateTopic`** (or another bounce-feedback action) — the IAM user's policy lacks the actions listed under [AWS SES](#1-aws-ses). Add them, then run `hatchkit doctor --fix`, or re-run `hatchkit add <project> listmonk-ses`.

**`hatchkit doctor` says the SNS subscription is pending confirmation** — SNS sent its confirmation request before `bounce.ses_enabled` was on, or it could not reach the Listmonk URL. Check that the URL works from outside your network, then run `hatchkit doctor --fix`. It subscribes again, and SNS sends a new confirmation request.

**Send fails: `554 ... not authorized to send`** — SES SMTP credentials are derived from the IAM secret. Don't paste the IAM secret directly into Listmonk. `hatchkit ses smtp --show-password` prints the *derived* password. Use that.

**`hatchkit listmonk user` stops: the API user exists, but no stored token works** — Listmonk shows a token only once. If you have the working token, store it with `security add-generic-password -U -s hatchkit -a listmonk:project:<project>:api-token -w` and run the command again. Otherwise run it with `--regenerate-token`, then `hatchkit sync` and redeploy right away.
