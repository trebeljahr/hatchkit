| Flag | Effect |
|---|---|

## `hatchkit setup` (alias: `init`)

One-time onboarding. Walks through every provider hatchkit knows about:

- GitHub (via `gh` CLI)
- Coolify (URL + token)
- Hetzner Cloud, DNS provider (INWX / Cloudflare), S3 (Hetzner / AWS / R2)
- GlitchTip, Plausible, Listmonk, AWS SES, Google Search Console
- GPU platforms — Modal, RunPod, Hugging Face, Replicate

Everything is optional; you'll be prompted again the first time a command actually needs that provider.

## `hatchkit create`

Scaffold a new project.

```bash
hatchkit create [options]
```

### Options

Every question the interactive stepper asks has a matching flag. A value
you pass is used as-is and **its prompt is skipped**; anything you leave
out is still prompted for. Partial flag sets are the normal case — this
is a hybrid mode, not an all-or-nothing switch.

Add `--yes` (alias `--non-interactive`) to take defaults for whatever is
still unset and hard-fail — naming the missing flag — instead of
prompting. That makes `create` CI-safe.

#### Run mode

| Flag | Effect |
|---|---|
| `--yes`, `-y`, `--non-interactive` | Never prompt. Defaults for unset values; hard-fail when a required one has no default. |
| `--dry-run` | Print the fully-resolved plan (including flag-supplied values) and write nothing. |
| `--config <path>` | Load a JSON file of `Partial<ProjectConfig>` overrides. Individual flags win over the file. |

#### Project

| Flag | Values / effect |
|---|---|
| `--name <name>` | Project name. Required with `--yes`. |
| `--domain <host>` | Public domain. Defaults to `<name>.<your root domain>`. |
| `--description <text>` | One-liner for `package.json` + Coolify. Pass an empty value to answer "none". |
| `--surfaces <value>` | `fullstack` · `split` · `backend` · `static` |
| `--topology <value>` | `single-origin` (default) · `split`. How the deploy is laid out across Coolify apps — see [Deployment topology](/docs/topology). |

#### Deployment

| Flag | Values / effect |
|---|---|
| `--deployment-mode <value>` | `coolify` · `gh-pages` · `cloudflare` · `scaffold-only`. `gh-pages` and `cloudflare` both require `--surfaces static`. |
| `--coolify-runtime <value>` | `image` (default for new projects) · `compose`. Image apps deploy each service separately. |
| `--deploy-target <value>` | `new` (provision a Hetzner box) · `existing` (reuse one). |
| `--server-size <value>` | `cpx21` · `cpx31` · `cpx41`. Only for `--deploy-target new`. |
| `--server-location <value>` | `nbg1` · `fsn1` · `hel1`. Only for `--deploy-target new`. |
| `--server-id <id>`, `--server-ip <ip>` | Coolify server to reuse. Both required with `--deploy-target existing` under `--yes`. |
| `--deploy` / `--no-deploy` | Run the deploy after scaffolding, or skip Terraform / Coolify / ML. |

#### Stack

| Flag | Values / effect |
|---|---|
| `--features <list>` | `websocket`, `stripe`, `analytics`, `s3`, `workspaces`, `token-client-auth`, `desktop`, `mobile`, `release`, `client-core`, `extension`, `server-migrations`, `scheduler`, `public-api`, `auth-account-security`, `i18n`, `raycast`, `mcp`. Comma-separated; pass empty for none. `extension`, `raycast` and `mcp` need a `fullstack` or `split` surface. `raycast` and `mcp` pull in `client-core`; `mcp` also pulls in `public-api`. |
| `--analytics-providers <list>` | `glitchtip`, `plausible` |
| `--services <list>` | `glitchtip`, `plausible`, `listmonk-ses`, `s3`, `email`, `search-console` |
| `--db-engine <value>` | `mongodb` · `postgres` |
| `--db-provider <value>` | `coolify` (provision a container) · `external` (you supply a URI) |

#### Storage

| Flag | Values / effect |
|---|---|
| `--s3-provider <value>` | `hetzner` · `r2` · `aws` · `existing` · `none` |
| `--s3-endpoint`, `--s3-bucket`, `--s3-access-key`, `--s3-secret-key` | Required with `--s3-provider existing`. Prefer `--config` for the secret key so it stays out of your shell history. |
| `--s3-region <region>` | Defaults to `us-east-1`. |

#### Email

| Flag | Values / effect |
|---|---|
| `--email <value>` | `none` · `transactional` · `mailing-list` · `both`. All non-`none` answers map to Listmonk + SES. |
| `--email-forwarding <off\|addr[,addr…]>` | Cloudflare Email Routing local-parts to forward to your inbox, or `off`. |
| `--email-catch-all` / `--no-email-catch-all` | Also forward `*@domain` (on by default when addresses are given). |

#### ML / GPU

| Flag | Values / effect |
|---|---|
| `--ml-services <list>` | `3d-sam-objects`, `3d-sam-body`, `3d-hunyuan`, `3d-trellis`, `3d-extraction`, `subtitles`, `image-recognition`, `background-removal`, `custom-hf` |
| `--gpu-platforms <list>` | `modal`, `runpod`, `hf`, `replicate`. First entry becomes the default `ML_BACKEND`. |
| `--custom-hf-model <owner/model>` | Required with `--ml-services custom-hf`. |
| `--custom-hf-gpu-type <type>` | GPU type for the custom HF endpoint. |

#### Repo

| Flag | Values / effect |
|---|---|
| `--scaffold` / `--no-scaffold` | Write the app repo, or skip straight to provisioning. |
| `--github` / `--no-github` | Create the GitHub remote, or skip it. |
| `--github-visibility <value>` | `private` · `public`. `--public` / `--private` are shorthands. |
| `--install` / `--no-install` | Run `pnpm install` after scaffolding. |
| `--local-dev[=<slug>]` | Enable the Tailscale/Caddy dev URL and optionally set its slug (defaults to the project name). Defaults on for new projects. |
| `--no-local-dev` | Skip local-dev wiring for this project. |

### Examples

Hybrid — name and stack from flags, everything else still prompted:

```bash
hatchkit create --name blog --surfaces static --deployment-mode gh-pages
```

Fully non-interactive, CI-safe:

```bash
hatchkit create --yes --name blog --domain blog.example.com \
  --surfaces fullstack --deployment-mode coolify --deploy-target new \
  --features analytics,s3 --analytics-providers glitchtip \
  --db-engine postgres --db-provider coolify \
  --email transactional --email-forwarding hello,support \
  --ml-services "" --public
```

### Flow

1. Prompts for name, domain, deploy target, features, services, ML services, **database engine** (MongoDB or Postgres), and **database provider** (Coolify-provisioned container or external URI).
2. Scaffolds the starter, strips unselected features, assigns unique ports. When `dbEngine: postgres` is selected, the starter's Mongoose stack is rewritten to Drizzle ORM + `pg` + better-auth's `drizzleAdapter`, and the `docker-compose` mongo service is swapped for a `postgres:16-alpine` container.
3. Auto-wires local-dev unless disabled: `.hatchkit.json` gets `localDev.slug`, `docs/dev-setup.md` is generated, and the Next/Vite dev plugin plus Caddy fragment are added.
4. Installs deps (if `pnpm` is available and you opt in).
5. `git init` + first commit + GitHub repo.
6. Optionally provisions GlitchTip/Plausible, Listmonk + SES, Email Routing, and Search Console via the same path as `hatchkit add`.
7. Generates Terraform tfvars + Coolify `.env`.
8. Runs Terraform (DNS + optionally server).
9. Runs Coolify app setup and pushes the dotenvx private key.
10. Deploys ML services and prints env endpoints to set.

## `hatchkit update`

Run **inside an already-scaffolded project** to add features additively.

```bash
cd my-app
hatchkit update --dry-run           # what would change
hatchkit update                     # pick interactively
hatchkit update --features desktop,mobile --yes
```

Reads `.hatchkit.json`, then adds selected features. Supported additions are `workspaces`, `token-client-auth`, `desktop`, `mobile`, `release`, `auth-account-security`, `client-core`, `extension`, `server-migrations`, `scheduler`, `public-api`, `i18n`, `raycast`, and `mcp`. Removal is not supported because it could delete user code. Remove files manually and update the manifest.

**Additive means additive.** A file the project already has is never overwritten, so a desktop shell whose main process moved into a bundler keeps it, and a hand-edited `desktop-release.yml` survives. The same holds inside `package.json`: a script or a dependency pin the project has changed away from the starter's shape is reported as kept, not replaced — including the `dev:desktop` command, which is only retargeted at a new native HMR port while it still has the generated shape. `hatchkit update --force` replaces those `package.json` pieces with the starter's current versions. It never overwrites files.

### The `workspaces` feature

Adds tenants, members, roles and invitations to a scaffolded app. Additive: it
writes new files and wires them into your router, auth config and Express app.
It never rewrites code you wrote, and a file you have edited is left alone and
named in the output.

What lands in the project:

| Path | Job |
|---|---|
| `packages/shared/src/membership.ts` | The contract: the closed role set, the capability flags, the refusal codes, the projection helpers. |
| `packages/server/src/models/WorkspaceMember.ts` | The app's own membership mirror — the only thing that grants access. |
| `packages/server/src/services/membership/` | The service layer. Every membership change goes through it. |
| `packages/server/src/auth/organization-lockdown.ts` | Answers 404 to every `/api/auth/organization/*` request. |
| `packages/server/src/trpc/routers/{workspaces,members,invitations}.ts` | The typed API — one line per procedure over the service. |
| `packages/server/src/rest/workspaces.ts` | The REST surface, over the same service. |
| `packages/server/src/ws/membership-sync.ts` | The realtime fan-out, projected per recipient. Written only with `websocket`. |
| `packages/client/src/app/invite/page.tsx` | The public invite page, at `/invite/?id=<id>`. |
| `packages/client/src/app/(protected)/members/page.tsx` | The members screen. |

Design points worth knowing before you change any of it:

- **better-auth's organization plugin stays installed** for its tables and for
  the server-side `auth.api.createOrganization` the signup hook calls, but every
  one of its HTTP endpoints answers **404**. Those endpoints write better-auth's
  `member` row and never the app's mirror, and they accept roles the app's own
  rules refuse — each was a way around those rules. A generated test hits all of
  them against the real library.
- **The mirror grants access. It is written last and deleted first**, so a crash
  mid-operation always leaves *less* access than intended, and re-running the
  operation finishes the job.
- **`owner` is reachable only by transfer** — never by an invitation or a role
  update — and a workspace can never be left with zero owners.
- **A foreign or cross-tenant id answers 404 before any permission is checked.**
  A 403 would confirm the id exists somewhere.
- **Invitations carry 96 CSPRNG bits** and are accepted on an email match rather
  than a verified address, so a self-host with no mail transport can still
  invite people — the UI shows a copyable link when a send fails.
- **Every request names its tenant.** An explicit tenant the caller is not in is
  404 and never falls back; a stale session default does fall back. Switching
  tenants in the client is a full page load, and everything cached is keyed by
  tenant.

With `websocket` off the membership events publish into a no-op, and the members
screen will not live-refresh. Everything else works.

### `extension`

Writes `packages/extension` (a development, a Chrome and a Firefox
build target declared in `manifest.config.ts`), the bridge that keeps
the extension signed in with the web app (`packages/shared`, plus the
page half and a `/device` approval page in the client), the server's
origin-trust rule, and a release workflow that uploads to the Chrome
Web Store and signs for addons.mozilla.org.

It builds on the shared client core, so it is refused on a `static` or
`backend` surface — there would be no page to drive the bridge, or no
server to trust the extension's origin.

Two things have to be set by hand after scaffolding, and nothing works
until they are:

- the extension's origin in the server's `TRUSTED_ORIGINS`
  (`pnpm run extension:id` prints it). The Firefox build's origin is a
  fresh random UUID per install, which no list can hold, so that one
  needs `TRUST_EXTENSION_ORIGINS=true` instead.
- `NEXT_PUBLIC_EXTENSION_IDS` in the web app's build env, or the bridge
  has nobody to message.

Re-running `hatchkit update` is safe: the extension's own source is
kept once it exists, and the workflow it owns is regenerated.

### The server platform features

`server-migrations`, `scheduler` and `public-api` write into `packages/server`
and run the same writer `hatchkit create` runs, so a project that skipped one at
scaffold picks it up here. Re-running is a no-op: a file whose contents already
match is left alone, and a file you have edited is reported and left untouched.
See [Server Platform](./server-platform).
| Flag | Effect |
| --- | --- |
| `--features <list>` | The feature set you want, comma-separated. Skips the picker. |
| `--dry-run` | Print the plan — the files each addition would copy — and write nothing. |
| `--yes`, `-y` | Don't prompt; accept the additions. |
| `--json` | Print the result as JSON. |

Adding a native shell also flips `packages/client/next.config.ts` to `output: "export"`. The shell loads `packages/client/out`, and a standalone build never writes that directory. If you have edited the config yourself, `update` leaves it alone and prints the one line you need to add.

Run it twice and the second run does nothing: files that already exist are never overwritten, so your edits survive.

## `hatchkit dev-setup`

Host-wide and per-project setup for stable HTTPS dev URLs over Tailscale:

```bash
hatchkit dev-setup init
hatchkit dev-setup status
hatchkit dev-setup enable
hatchkit dev-setup disable
```

### What it automates

| Command | Effect |
|---|---|
| `dev-setup init` | Writes `~/.config/dev/Caddyfile`, writes/loads the launchd Caddy job, registers `tailscale serve --tcp=443`, and upserts `*.local.<your-domain> A <tailnet-ip>` when Cloudflare credentials are available. Custom `--domain` values must use the dedicated `local.` prefix. |
| `dev-setup status` | Prints the Local-dev checks from `hatchkit doctor`. |
| `dev-setup enable [--slug <s>] [--port <p>] [--project-dir <path>]` | Retrofit an existing project: writes the Caddy fragment, generates `docs/dev-setup.md`, patches supported framework config, adds the dev plugin package, and persists `localDev.slug`. |
| `dev-setup disable` | Removes the project Caddy fragment and generated docs file. Host-wide Caddy/Tailscale setup remains for other projects. |

`dev-setup init` is one-time per machine and idempotent. New projects already run the per-project wiring during `hatchkit create`, so `dev-setup enable` is mainly for older projects.

See [Local Dev On Mobile](./local-dev-mobile) for the Tailscale + Caddy + Capacitor flow.

## `hatchkit server add`

Retrofit the Hatchkit server surface into a static project.

```bash
cd my-app
hatchkit server add
```

This is a local scaffold step only. It copies `packages/server`, restores shared server types, updates workspace/root scripts, flips `.hatchkit.json` from `static` to `fullstack`, and moves `gh-pages` / `cloudflare` manifests back to `coolify` because a static host cannot run a backend.

After reviewing the diff:

```bash
pnpm install
pnpm run typecheck
hatchkit adopt --resume --regenerate-pipeline
```

`adopt --resume` is the deploy wiring step: Coolify, DNS, GitHub Actions secrets, dotenvx key push, and provider provisioning stay there so existing rollback and provider guard rails apply.

Options:

| Flag | Effect |
|---|---|
| `--server-dir <path>` | Destination for the server package. Default: `packages/server`. |
| `--shared-dir <path>` | Destination for the shared package. Default: `packages/shared`. |
| `--yes`, `-y` | Skip confirmation. |
| `--dry-run` | Show planned local changes without writing. |
| `--json` | Machine-readable result. |

## `hatchkit add`

Provision observability / email / search services for an **existing** project. Creates project-scoped resources for each selected service.

```bash
hatchkit add                                     # fully interactive
hatchkit add raptor-runner                       # prompts for services
hatchkit add raptor-runner all                   # all services
hatchkit add raptor-runner glitchtip,listmonk-ses # explicit list
hatchkit add raptor-runner search-console        # verify domain + add Search Console property
```

### Services

| Name | Creates | Returns |
|---|---|---|
| `glitchtip` | GlitchTip project | `SENTRY_DSN` + `GLITCHTIP_DSN` (server), `NEXT_PUBLIC_SENTRY_DSN` + `PUBLIC_GLITCHTIP_DSN` (client); also Coolify `SENTRY_DSN` and the `NEXT_PUBLIC_SENTRY_DSN` repo variable |
| `plausible` | Plausible site | `NEXT_PUBLIC_PLAUSIBLE_DOMAIN`, `NEXT_PUBLIC_PLAUSIBLE_SCRIPT_URL` |
| `listmonk-ses` | SES sending identity, Listmonk lists and templates | `LISTMONK_*`, `SES_FROM_EMAIL` |
| `s3` | Project object-storage buckets and credentials | `R2_*` or provider-specific S3 keys |
| `email` | Cloudflare Email Routing rules | no env; DNS MX/SPF/DMARC + forwarding rules |
| `search-console` | Google Search Console domain property | no env; DNS TXT verification |

| `stripe` | Per-project Stripe keys + a webhook endpoint per mode | `STRIPE_SECRET_KEY`, `STRIPE_PUBLISHABLE_KEY`, `STRIPE_WEBHOOK_SECRET` |

`stripe` and `signing` are standalone targets — run them by name; they are not part of `all`.

Values are written into the project, never to stdout: production values encrypted into `.env.production`, development values into the gitignored `.env.development.local`. The committed `.env.development` keeps only local defaults; `add` moves any provisioned credential it finds there into `.env.development.local` and warns. A 0600 copy of every value is also cached under `<config-dir>/provisioned/<project>.*.env`.

A new GlitchTip project's platform is `javascript-node` when a server reports to it (backend, fullstack, the `-server` project of a split one). A client-only project (static, or split `-client`) gets `javascript-nextjs` when the client's `package.json` depends on `next`, else `javascript-browser`.

### GlitchTip DSN delivery

The env files alone do not reach a deployed app, so `add … glitchtip` also writes the DSN to the two places production reads it:

- **`SENTRY_DSN` on the server's Coolify app.** The starter's compose file passes `SENTRY_DSN: ${SENTRY_DSN:-}`, so Coolify creates the key with an empty value. dotenvx never overrides a variable that is already set, even to an empty string, so an empty Coolify value hides the DSN in `.env.production`. The server reads it at boot: redeploy the app afterwards.
- **The `NEXT_PUBLIC_SENTRY_DSN` repo variable** (`gh variable set`). The client build inlines it from `vars.NEXT_PUBLIC_SENTRY_DSN`; the next client build picks it up. `add` warns when no workflow in the checkout reads that variable.

Each write is read back. A missing key, an empty value, a `CHANGE_ME_` placeholder, a DSN on the same GlitchTip host, or the same key under another host (rendered while `GLITCHTIP_DOMAIN` was wrong) is replaced. A DSN for another host (for example sentry.io) is kept and reported. A Coolify token without `read:sensitive` only creates a missing key. With `--no-write` nothing changes: `add` names the Coolify app it would write and prints the exact `gh variable set` command.

`add` refuses a DSN whose host is not the configured GlitchTip URL. GlitchTip builds every DSN from its `GLITCHTIP_DOMAIN` setting, and a wrong value (the compose default is `https://glitchtip.example.com`) sends every event elsewhere. Fix the setting, redeploy GlitchTip, and re-run with `--adopt`.

For a project that already has GlitchTip, `hatchkit add <project> glitchtip --adopt` re-reads the existing project's DSN and writes it under every name and to both targets. This is the repair for a project wired before `add` wrote `SENTRY_DSN`.

## Deferred steps

Every service above is **optional**, and so is every credential prompt behind it. If you pick a service and then discover you don't have the token to hand, answer **no** at the "Set up X now?" gate. That step is skipped; the rest of the run continues and finishes normally.

The same applies when a provider fails mid-run — a 401, a timeout, an unreachable host. Only genuinely fatal problems (a name collision with an existing resource, Ctrl+C) still abort.

Each skip is recorded three ways:

1. **End-of-run summary** — a `Configured` / `Deferred` block with the exact follow-up command per skipped item.
2. **`.hatchkit.json`** — under `deferred[]`. Labels, reasons, and CLI commands only; never a credential.
3. **`hatchkit status` and `hatchkit doctor`** — both keep reporting them until they're done. `doctor` shows them as `deferred`, distinct from `fail`, and does **not** exit non-zero for them.

```bash
hatchkit status            # "2 steps deferred" + the command for each
hatchkit status --json     # `deferredSteps[]` on the StatusSnapshot
hatchkit add raptor-runner s3   # finish one; the entry clears itself
```

Re-running a deferred step is safe: `hatchkit add` refuses services whose credentials are already in the env files, so nothing is provisioned twice. `hatchkit adopt --resume` retries deferred steps for the same reason — they wrote no env keys the first time round.

Nothing is rolled back for a deferral. A declined step created no remote resource, so there is no partial state to undo.

## `hatchkit cloudflare`

Serve a static repo from Cloudflare Workers Static Assets, where asset requests are free and unmetered. Writes `wrangler.jsonc`, `.node-version`, `public/_headers` and a `cloudflare/wrangler-action@v4` workflow, then sets the repo-level CI secrets.

```bash
cd my-site
hatchkit cloudflare
hatchkit cloudflare --undo [--dry-run] [--yes]
```

Needs `hatchkit config add cloudflare` first (account ID + the Cloudflare operator token; see [Providers → Cloudflare](./providers#cloudflare)). `hatchkit doctor` probes every permission and names every missing one.

The custom domain is attached automatically **only** when the hostname has no existing DNS records. Cloudflare refuses to attach over existing records (`code: 100117`), and clearing them first means downtime — so for a live domain hatchkit prints the records, the cutover order, and stops.

Full guide: [Cloudflare Workers](./cloudflare).

## `hatchkit gh-pages`

Wire GitHub Pages for the **current repo**. Run it from inside any repo — a sprite tool, a landing page, a docs folder — and it'll detect what's there, enable Pages, write the deploy workflow, and (optionally) configure a custom domain end-to-end.

```bash
cd my-sprite-tool
hatchkit gh-pages
```

### What it detects

| Kind | Trigger | Workflow generated |
|---|---|---|
| `static` | `index.html` at the repo root, no `build` script | checkout → `upload-pages-artifact` → `deploy-pages` |
| `node-build` | `package.json` with a `build` script (pnpm / npm / yarn / bun auto-detected from lockfile) | install → build → upload build output → deploy |
| `docusaurus` | `docusaurus.config.{ts,js}` present | Node + `docusaurus build` → upload `build/` → deploy |
| `jekyll` | `Gemfile` + `_config.yml` at the root **or** under `docs/` | Ruby + `bundle exec jekyll build` → upload `_site` → deploy |

For `node-build`, the publish dir is guessed from the build command (`vite` → `dist`, `react-scripts` → `build`, `astro` → `dist`, `next` → `out`) and you confirm interactively.

### Custom domain

If you opt in:

1. Calls `PUT /repos/:owner/:repo/pages -f cname=<domain>` to register it with Pages.
2. Writes a `CNAME` file into the published folder (or `public/` for node builds, `static/` for Docusaurus).
3. Wires DNS at your provider:
   - **Cloudflare** — uses the token in your keychain; creates/updates `A` records (apex) or a `CNAME` (subdomain) to `<user>.github.io`. Idempotent.
   - **INWX / manual** — prints the records you need to add yourself.

### Good fits

- Sprite editors, palette tools, one-off demos (plain `index.html`).
- Vite / Astro / CRA static sites (client-side only).
- Docusaurus and other SSGs whose output is pure HTML.
- A `docs/` folder inside a larger monorepo (like this one).

### Not a good fit

- Anything that needs a running server (websockets, MongoDB / Postgres, auth sessions, server-rendered Next). Use `hatchkit create` with the full-stack flow for those.

## `hatchkit migrate-runtime`

Moves a deployed project from a Coolify Docker Compose app to Docker Image
apps, so a push no longer takes the site down. See
[Deploys without downtime](/docs/topology#deploys-without-downtime-the-runtime)
for why.

```bash
hatchkit migrate-runtime [app…] --dry-run    # the plan, nothing changed
hatchkit migrate-runtime [app…]              # asks before it starts
hatchkit migrate-runtime [app…] --rollback   # back to the compose app
hatchkit migrate-runtime [app…] --cleanup    # delete the stopped compose app
```

With no app named, it takes the compose apps of the project in the current
directory. The steps:

1. Renames `<app>` to `<app>-legacy-compose`.
2. Creates a Docker Image app per compose service. It copies the image, the
   env, the port and every hostname, including hosts named only in
   hand-written Traefik labels, and adds a health check.
3. Deploys the new app while the old one serves, then checks it through
   Traefik on a private verification hostname.
4. Stops the old app, points the repo's `COOLIFY_*_RESOURCE_UUID` secret (and,
   on a repo using signed deploys, the new app's own deploy secret) at the new
   one, and records `"coolifyRuntime": "image"` in `.hatchkit.json`.

A failure before step 4 leaves the old app serving, with only the rename
undone. Every step is recorded under the hatchkit config directory, so
`--rollback` and `--cleanup` never guess.

| Option | Effect |
|---|---|
| `--health-path <service>=/path` | Health endpoint for one service. Default: `/api/health` for a service named `server`, `api` or `backend`, `/` otherwise. |
| `--keep-live-tag` | Keep the deployed commit's tag. Use it when the repo's workflow already pins image tags. |
| `--no-secrets` | Leave the GitHub Actions secrets alone. |
| `--carry-volume <service>=<volume>` | Mount this compose named volume on the new app. Repeat it for each volume. |
| `--same-json <service>=/path:<field>` | Require the same JSON field value on production and on the new app before any traffic moves. |
| `--yes` | Don't ask. |

It refuses apps with a datastore service or a volume, apps that publish host
ports, and apps that never deployed.

### Where the Traefik checks go

The checks send a GET straight to Traefik, with the hostname as the `Host`
header. Hatchkit uses the first address that applies:

1. `HATCHKIT_TRAEFIK_ADDRESS`, an IP address or hostname you set.
2. The tailnet IPv4 of the backup host (`providers.backups.hosts`, read with
   `tailscale ip -4`), when that host is the app's Coolify server.
3. The server's public IPv4.

The run prints the address it uses. `--dry-run` also sends one GET there and
prints Traefik's answer. A server that accepts 80/443 only from Cloudflare
drops a request to its public IPv4, so it needs option 1 or 2.

### Carry a named volume

Some apps keep their state in a file. A SQLite database in a Docker volume is
the common case, and there is no managed database to move it to. Name the
volume and the new app mounts it:

```bash
hatchkit migrate-runtime \
  --carry-volume client=auth-data \
  --health-path client=/api/health \
  --same-json client=/api/health:databaseId \
  --dry-run
```

The new app mounts the same Docker volume the compose app created,
`<compose app uuid>_<volume>`. Hatchkit copies no data. The plan prints the
Docker volume and the mount path, and it checks both against the storage
Coolify recorded for the compose app.

**Two containers write the volume at the same time.** This happens during
verification, until the compose app stops. It happens again for the overlap of
every later rolling deploy. Carry a volume only when the app is built for two
writers. For SQLite that means WAL mode, a busy timeout, and background jobs
that tolerate a second runner.

`--same-json` protects against a wrong mount. A new app on an empty volume can
start, create a fresh database and pass its health check. With the flag,
hatchkit reads one JSON field from the production URL and from the new app's
private verification host. The values must be equal. If they differ, the run
stops, the new app gets no public route, and the compose app keeps serving.
Hatchkit reads the field once more on the public URL after the cutover.

Coolify 4.0.0-beta.469 can't create a storage through its API. On that version
the run pauses once and prints one step for the dashboard: open the new app's
Persistent Storage page and add a Volume Mount with the mount path.
Hatchkit then renames that storage to the Docker volume, reads it back, and
deploys. A Coolify version that can create a storage through the API needs no
manual step.

Only a plain named volume can be carried. Hatchkit still refuses bind mounts,
read-only mounts, and volumes with `external`, `name` or driver options.

`--rollback` and `--cleanup` keep the volume. After the move, Coolify lists
the volume as a storage of the new app. If you delete that app in the Coolify
dashboard with "Delete volumes" ticked, Coolify deletes the data.

A registered backup that reads the volume by host path keeps running
unchanged, because the path stays the same. A backup that reads the compose
app's container still blocks the move.

## `hatchkit sync`

Pushes the manifest's view of the project onto Coolify: which applications
should exist, which domains hang off which compose services, and whether
Traefik's path-prefix stripping should be on. Idempotent.

```bash
hatchkit sync --dry-run    # read-only: print the diff
hatchkit sync              # push it
hatchkit sync --deploy     # push it, then redeploy so Traefik regenerates labels
```

`--deploy` is what makes a routing fix take effect: Coolify regenerates a
container's Traefik labels on deploy, not when the application record is
PATCHed.

Before it creates, patches or deploys anything, sync checks that the commit
Coolify will **clone** actually contains the compose file each application
builds from. Coolify never deploys your working tree — it clones
`origin/<branch>` and reads `base_directory` + `docker_compose_location` out of
that commit, so a compose file you have written but not pushed does not exist as
far as the deploy is concerned. Sync stops rather than build that state, and
prints the commit it checked:

```
✗ Coolify deploys origin/main — origin/main @ 26fdc06 "Initial scaffold"
    local main @ 8f5ddaf "chore: split the compose file in two"
    local is 55 commit(s) ahead of origin/main — Coolify deploys origin/main, not your working tree.
    docker-compose.server.yml is missing from origin/main — it exists locally but has never been pushed (tracktime-server).
    Fix: git push origin main
```

This is worth its own guard because of how the failure presents. Coolify's
deployment log shows `git ls-remote`, `git clone`, `git fetch` and `git log -1`
all succeeding and then ends with `fatal: could not read Username for
'https://github.com'` — an authentication error for authentication that is
working fine. The `git log -1` line in the same log names the commit that was
actually cloned, and that is the line worth reading.

The check runs `git fetch` first so it isn't answering from a stale
remote-tracking ref — that fetch is the only thing it writes, and it writes
nothing outside `.git/refs/remotes`.

`hatchkit doctor` and `hatchkit inventory` report the same fact for a project
whose manifest (or live Coolify app) declares a compose location.

Sync **refuses** to push routing that names a compose service the project
doesn't declare. Coolify answers such a PATCH with a 200 OK and then emits no
Traefik labels at all, so the app 503s every request — a silent outage that
looks like a successful sync.

On a single-origin project, sync first looks for an application named after
the project. A Docker Image app with that name is the whole deployment: it is
what `migrate-runtime` makes of a compose app that ran one service. Sync sets
its domains to the manifest's `domain` plus `aliases[]`. It creates no
`<name>-client` or `<name>-server` app beside it. `--dry-run` prints the exact
`domains` value it would send. If the manifest says `coolifyRuntime: "image"`
but that application is still a Docker Compose app, sync creates nothing and
changes nothing on it.

| Flag | Effect |
|---|---|
| `--dir <path>` | Project root (defaults to cwd). |
| `--dry-run` | Show the diff without touching Coolify. Read-only. |
| `--deploy` | Redeploy each changed app so the new labels go live. |
| `--force` | Push through a Coolify domain-conflict (409). |
| `--no-preflight` | Skip the deployed-ref check. For a repo git can't answer for (a shallow clone, a remote only Coolify can reach) — not for pushing past a finding. |
| `--yes`, `-y` | Accept the `TRUSTED_ORIGINS` diff without a prompt. |
| `--no-native-origins` | Skip the native-client origins pass. |
| `--json` | Machine-readable output. |

### Native clients and `TRUSTED_ORIGINS`

A project with the `mobile` or `desktop` feature ships a shell
that loads the client from its own origin. better-auth answers
`403 INVALID_ORIGIN` to an origin that is not in `TRUSTED_ORIGINS`, before it
checks the password.

| Feature | Origins |
|---|---|
| `mobile` (Capacitor) | `capacitor://localhost` (iOS), `https://localhost` (Android) |
| `desktop` (Electron) | `app://-` |

`hatchkit create`, `adopt`, `update` (after it adds a native feature) and `sync`
merge these into `TRUSTED_ORIGINS` on the **server** Coolify app. The client
app is never touched.

- Existing entries keep their order. Missing origins are appended. Nothing is
  removed.
- The before/after list is shown, and the write waits for a yes. `--dry-run`
  stops after the diff.
- The value is read back from Coolify after the write. A write that did not
  land is an error.
- If the Coolify token cannot read env values (no `read:sensitive`), nothing is
  written.
- The server reads the list at boot. Use `--deploy`, or redeploy by hand.

Trusting `https://localhost` in production means a page served from
`https://localhost` on a user's machine also passes the origin check. Capacitor
on Android needs that origin.

Do not test this with a bare curl. better-auth only enforces the origin check on
a cookieless sign-in when the request carries `Sec-Fetch-*` headers. The deploy
workflow's "Verify native clients can sign in" step sends them.

See [Deployment topology](/docs/topology) for what the two topologies route,
and for repairing a project deployed before 0.2.19.

## `hatchkit doctor`

Runs read-only checks against configured providers, including Coolify, Hetzner, Cloudflare, SES, and Listmonk. Reports `ok` / `fail` / `warn` / `deferred` / `not configured` and exits non-zero if any check fails. A warning prints its fix without failing the run.

With Coolify configured, `doctor` also reads the compose file of every `dockercompose` app on the instance. It warns about each service that runs a `ghcr.io/...` image on a mutable tag (`:latest`, `:main`, no tag) without `pull_policy: always`. Docker starts the image it cached for that tag, so a deploy can finish green, report `running:healthy`, and still serve the previous build. The hint names the app, the repo and the compose file. For a hatchkit project, `hatchkit update` or `hatchkit regen-infra` adds the line.

It also warns about Coolify apps whose `SENTRY_DSN` is set but empty. The empty value hides the DSN in the app's `.env.production` (see [GlitchTip DSN delivery](#glitchtip-dsn-delivery)); `hatchkit add <project> glitchtip --adopt` fills it. Values are compared, never printed.

The GlitchTip row reads one project's DSN and fails when its host is not the configured GlitchTip URL. That means the server's `GLITCHTIP_DOMAIN` is wrong and every DSN it hands out sends events elsewhere.

Run from inside a project whose Dockerfile's final stage is `FROM nginx`, and `doctor` checks that the image gets a config under `/etc/nginx/`. nginx's stock config maps a URL straight onto a file, so a reload on a client-side route or on a page URL without `.html` returns a 404. Projects adopted before hatchkit wrote `nginx.conf` have this Dockerfile. The warning prints the config for your build and the one `COPY` line to add. `hatchkit adopt --resume --regenerate-pipeline` also fixes it, but it re-renders the Dockerfile, compose file and deploy workflow too.

With SES and Listmonk configured, `doctor` checks the [bounce feedback path](/docs/email#bounces-and-complaints) across the whole SES account. It fails on a verified identity whose Bounce or Complaint notifications go to no SNS topic, on a missing or unconfirmed subscription from the `ses-feedback-listmonk` topic to Listmonk's SES webhook, on account suppression that doesn't cover `BOUNCE` and `COMPLAINT`, and on Listmonk bounce settings that are off. A read the IAM policy doesn't allow is a `warn` that names the missing action.

Run from inside a project directory and it also lists that project's [deferred steps](#deferred-steps) with the command to finish each one. Deferred steps never make `doctor` exit non-zero — they're work you postponed, not a broken credential.

With a backup host configured, `doctor` also runs the [host integrity scan](#hatchkit-host-integrity) on each backup host and reports whether the daily check is installed and mailing. It also shows one [update watch](#hatchkit-host-updates) row for the shared services on every backup host.

`hatchkit doctor --fix` adds one step after the report: for each failure that doctor can repair itself, it asks `y/N` (default No) and applies the repair on a yes. Today that covers a project's Listmonk tx template that HTML-escapes the email body, and each broken piece of the SES bounce feedback path. `--yes` applies every offered repair without asking. Without a terminal and without `--yes`, nothing is applied. `--fix` is ignored with `--json`, so `doctor --json` stays read-only.

## `hatchkit host integrity`

Scans a backup host (a Coolify server in `providers.backups.hosts`) over Tailscale SSH for signs that a container was taken over. It only reads. With several backup hosts, `--host <name>` picks one.

```bash
hatchkit host integrity [--cpu-window <seconds>] [--json]   # scan now; exits 1 on a finding
hatchkit host integrity install [--dry-run]                 # daily check that mails findings
hatchkit host integrity uninstall [--dry-run]
hatchkit host integrity test                                # send a test mail
```

It reports:

- a process whose binary was deleted from disk;
- a container process that does not run a binary its image ships, or runs one under a name that neither the binary nor the image family explains (Node's `MainThread`, `next-server`, Postgres, Mongo, Redis, ClickHouse, Erlang, Traefik, Coolify's s6 helpers, …). A binary the container added or changed in its writable layer, or runs from a volume, is not one its image ships;
- a new file in `/tmp`, `/var/tmp` or `/dev/shm` of a container, or a process that runs a binary from one of them;
- a container above 50 % of one core over the CPU window;
- an outbound TCP peer outside private ranges and [Cloudflare's published ranges](https://www.cloudflare.com/ips/), connected in at least half of the samples. The scan samples once a minute; a shorter window samples at both ends. A peer behind Cloudflare is not reported, because apps reach R2, Workers and every proxied hostname there.

The report never holds environment values, command lines or file contents. Process and file names are escaped, because an attacker chooses them. A check that could not run (a failed `docker diff`, a container that restarted inside the window, a container on the host network) is listed as not checked, never as clean. The default window is 10 seconds, and a CPU finding over a window shorter than 50 minutes is a warning; `--cpu-window 3600` averages over an hour.

`install` writes the script next to the backup runner in `/opt/hatchkit-backups` and enables a daily timer (05:00 UTC). Each run samples for one hour, then mails its findings through the backup-alert SMTP that [`hatchkit backup alerts`](#other-command-routes) set up. A run with findings mails every day; the first clean run after them sends one all-clear. A run that systemd stops before it finishes sends its own mail. `install` refuses a host without the backup runner or its alert mail, and runs one read-only scan before it writes anything. `--dry-run` runs only that scan and lists what the first mail would contain.

When a finding is expected and you know what causes it, add its `allow` entry from `--json` to `/etc/hatchkit-backups/host-integrity.json` on the host. The keys are `processes` (container-name or image glob to process names), `tempFiles` (path globs), `peers` (CIDRs, for every container), `peerContainers` (globs whose outbound peers are not checked) and `cpuLimits` (glob to percent of one core). Deleted binaries, executables in temp dirs and binaries run from a temp dir have no exception: restart the container once you know why.

## `hatchkit host updates`

Reads the running version of each shared service on every backup host over Tailscale SSH and compares it with upstream security advisories. It only reads.

```bash
hatchkit host updates [--host <name>] [--json]         # check now; exits 1 on a finding
hatchkit host updates install --host <name> [--dry-run] # weekly check that mails findings
hatchkit host updates uninstall --host <name> [--dry-run]
hatchkit host updates test --host <name>                # send a test mail
```

It watches Coolify, Traefik (`coolify-proxy`), Plausible CE, Listmonk, Uptime Kuma, GlitchTip and ClickHouse. For each running container of those images it reports:

- the running version. It comes from the image's version label or env, else from a tag that names one release, else from the binary in the container. A floating tag such as `traefik:v3.6` or `louislam/uptime-kuma:2` names a line, not a release;
- every `high` or `critical` advisory in the repository's [GitHub security advisories](https://docs.github.com/en/code-security/security-advisories) whose vulnerable range covers that version, with its fixed version and the latest release. A version at or past a patched release on its own branch is not covered. GlitchTip publishes no advisories; it is compared with its latest GitLab tag only;
- Coolify's own auto-update failing: the newest `/data/coolify/source/upgrade-*.log` ends in an error, with the number of failed runs in a row;
- Cloudflare's [published IP ranges](https://api.cloudflare.com/client/v4/ips) differing from the snapshot the origin firewalls were built from (`update-watch-cloudflare.json`), from the host's `HATCHKIT-CF` iptables chain, or from a Hetzner firewall that allows 80/443 only from a source list. An origin that allows only Cloudflare drops traffic from a new edge. `doctor` reads the Hetzner firewalls with your Hetzner token; the weekly check sees the snapshot and the chain.

A check it could not make (a feed error, a version nothing names, an advisory range it cannot read) is listed as not checked, never as clean. `hatchkit doctor` and `hatchkit host updates` read GitHub through your `gh` login; whatever fails there, the host reads itself.

`install` writes the script next to the backup runner in `/opt/hatchkit-backups` and enables a weekly timer (Monday 06:00 UTC), so a new advisory is flagged within a week. Each run mails its findings and anything it could not check through the backup-alert SMTP that [`hatchkit backup alerts`](#other-command-routes) set up; the first clean run after them sends one all-clear. `install` refuses a host without the backup runner or its alert mail, and runs one read-only check before it writes anything. `--dry-run` runs only that check.

## `hatchkit plausible merge`

Folds one Plausible Community Edition site into another site that already exists, with its history. Use it when a project moved to a new domain, the new domain already has a site, and the old site now only redirects. `hatchkit plausible rename` cannot do this: it uses the Sites API, which Community Edition does not serve, and a rename cannot target a domain that has a site. Plausible itself has no merge.

```bash
hatchkit plausible merge <old-domain> <new-domain> --dry-run   # every read and check, writes nothing
hatchkit plausible merge <old-domain> <new-domain>             # asks before it writes
hatchkit plausible merge <old-domain> <new-domain> --yes [--json]
```

It runs on the backup host that runs Plausible, over Tailscale SSH. `--host <name>` picks the host; without it, hatchkit uses the only backup host, or the one host that runs Plausible. It finds the containers `plausible-<uuid>`, `plausible-db-<uuid>` and `plausible-events-db-<uuid>` by name; `--service <uuid>` picks one when a host runs several. The database names come from `DATABASE_URL` and `CLICKHOUSE_DATABASE_URL` inside the app container, so the database password does not leave it.

It refuses, before it writes anything, when:

- one of the two sites does not exist;
- the two sites' event time ranges overlap. A pageview that both sites recorded would count twice. `--allow-overlap` merges anyway;
- the old site's events all come after the new site's. The domains are probably swapped, and the merge would delete the site that still receives traffic;
- the old site holds imported data (`imported_*` tables). Deleting the site deletes the import, and the merge does not carry it;
- backup tables of an earlier merge of the old site exist. That merge stopped part-way; finish or undo it by hand first;
- a goal it would copy has the display name of a different goal on the new site.

Then, in this order:

1. A `pg_dump -Fc` of the Postgres database to `/root/plausible-site-merge-<date>/plausible-db-site<old id>-<time>.pgdump` on the host, and the two sites' rows of `events_v2`, `sessions_v2` and `ingest_counters` to `premerge_<date>_site<old id>_*` tables in ClickHouse.
2. The old site's rows are copied from those tables to the new site id (`SELECT * REPLACE (<new> AS site_id)`; `ingest_counters` also gets the new domain). It checks the new site's counts before it deletes anything.
3. The new site's `native_stats_start_at` and `stats_start_date` move back to the old site's when those are earlier. Otherwise the dashboard hides the old events.
4. Goals that the new site does not have are created with `Plausible.Goals.create` (through `bin/plausible rpc`).
5. The old site is deleted with `Plausible.Site.Removal.run/1`, then its ClickHouse rows (`ALTER TABLE … DELETE`, `mutations_sync = 2`).
6. It prints events, sessions (the sum of `sign`) and unique visitors of both sites, before and after, and fails when the new site has fewer events or sessions than the two sites had together.

When the old site recorded an event in the last hour, the plan says so: events it receives between the copy and the delete are lost. The new site keeps its own timezone. If a step after the backups fails, the error lists how to undo the merge from the dump and the backup tables. Drop the `premerge_*` tables when nobody needs the rollback; they are also in the daily snapshot of the ClickHouse volume. Update `data-domain` in the deployed app if it still reports the old domain.

## `hatchkit audit cloudflare`

Reports what is on the Cloudflare account that hatchkit did not create. hatchkit's operator token can mint account API tokens, so a leaked copy owns the account, and an attacker's first move is a second token. A Worker runs this check every 6 hours and mails you when it finds something. The check reads with its own read-only token and changes nothing on Cloudflare.

```bash
hatchkit audit cloudflare [--json] [--hours 36]   # run it here; exits 1 on an alert
hatchkit audit cloudflare accept token:<id>=<why> worker:<name> …
hatchkit audit cloudflare accept --inventory      # first run: keep every current non-token resource
hatchkit audit cloudflare forget <kind>:<value>
hatchkit audit cloudflare set-token               # the read-only Cloudflare token, into the keychain
hatchkit audit cloudflare set-ses-key             # the Worker's own SES key, into the keychain
hatchkit audit cloudflare test-mail --from <sender> --region <aws region>
hatchkit audit cloudflare deploy --from <sender> [--region <aws region>] [--dry-run]
hatchkit audit cloudflare publish                 # re-sign and upload the expected state
```

It reports:

- an account-owned or user-owned API token, disabled or not, that is not a recorded per-Worker CI token, a recorded per-project R2 token, an accepted token, or a `hatchkit-terraform-*` token younger than one hour. Tokens and OAuth clients are matched by id; a name proves nothing;
- audit-log entries (v2) made by the operator token outside a recorded hatchkit run, by an unknown token, by the Global API Key, or by an OAuth app that is not allowed (Wrangler and the two Cloudflare MCP servers are);
- a Worker, R2 bucket, zone, Email Routing destination, member or OAuth client nobody accepted, and an Email Routing rule that forwards to an unknown address or Worker.

A list it cannot read, or one longer than the page cap, counts as a failure, never as clean. The expected state comes from hatchkit's own records: `cloudflareDeployTokens`, run ledgers, the `.hatchkit.json` files under `~/projects` and `~/work`, accepted entries, and the times hatchkit held the operator token. `--expected <file>` or `HATCHKIT_CLOUDFLARE_EXPECTED` replaces it.

`deploy` creates the R2 bucket and the Worker `hatchkit-audit` with the operator token, sets its secrets from the keychain, adds the cron trigger `17 */6 * * *`, and publishes the expected state. Each run looks at the last 7 hours of the audit log. It mails through SES only when an alert appears that the last mail did not list, when alerts are still open 24 hours after the last mail, or when the run cannot finish. There is no all-clear mail. Everything in the bucket is signed with a key that only the keychain and the Worker hold, so the operator token alone cannot forge the expected state or a run window. hatchkit uploads its run window, and republishes the expected state, during every command that uses the operator token.

The operator token can still replace or delete the Worker. So a local run also checks that the Worker's deployment is the one hatchkit deployed, that the cron trigger and secrets are there, and that the last run is less than 8 hours old.

The read-only token is a user token (My Profile → API Tokens) with User · API Tokens · Read; Account · Account API Tokens · Read, Account Settings · Read, Workers Scripts · Read, Workers R2 Storage · Read, Email Routing Addresses · Read; Zone · Zone · Read and Email Routing Rules · Read on all zones; optionally Account · OAuth Clients · Read. The SES key belongs to an IAM user that may only call `ses:SendEmail` from the sender to your address.

## `hatchkit infra`

Runs one of hatchkit's own Terraform stacks, the ones that belong to no single project. Today that is `ota-updates`: the live-update endpoint `ota.ricoslabs.com` (one Worker and one R2 bucket) for the Capacitor apps. See `infra/ota-updates/README.md`.

```bash
hatchkit infra plan ota-updates             # saves tfplan and lists every change
hatchkit infra apply ota-updates            # applies exactly that saved plan
hatchkit infra output ota-updates [name]    # reads the local state; no token
```

`plan` and `apply` each mint a Cloudflare account token with only the grants the stack lists, valid for one hour, and revoke it when the run ends. Terraform gets it as `CLOUDFLARE_API_TOKEN`; the operator token never reaches Terraform. The minted token is read back first, and the run stops when its policy is broader than asked. Its name, `hatchkit-terraform-<stack>-<time>`, is one the Cloudflare audit expects.

`plan` marks each resource that must be replaced or destroyed. `apply` refuses without a saved plan, and Terraform refuses a plan the state has moved past. After an apply the stack's Workers and buckets are accepted in the Cloudflare audit, and the expected state is republished when the audit Worker is deployed.

The Terraform state stays in the stack directory of the checkout that ran it (gitignored). Run `infra` from the same checkout every time.

## `hatchkit mac-runner`

Runs a private repo's Apple jobs (macOS and iOS builds) on this Mac instead of GitHub's macOS runners. In a private repo, a macOS minute counts as ten Linux minutes. In a public repo it is free, so the command refuses public repos.

```bash
hatchkit mac-runner on                        # set APPLE_RUNNER=hatchkit-mac on this checkout's repo
hatchkit mac-runner run build-macos.yml -f upload=false   # dispatch, then host the run's Apple jobs here
hatchkit mac-runner serve                     # host what a tag push or an agent queued
hatchkit mac-runner serve --run 1234567890    # host one run
hatchkit mac-runner status [--json]           # the variable, and the jobs waiting for this Mac
hatchkit mac-runner off                       # Apple jobs go back to GitHub
```

The Apple jobs choose their runner with `runs-on: ${{ vars.APPLE_RUNNER || 'macos-15' }}`. The starter's `mobile-release.yml` and `desktop-release.yml` and the signing template `build-ios.yml` already do this. With the variable unset, nothing changes. With it set, the jobs wait for this Mac. The rest of the workflow stays on GitHub: artifacts, TestFlight, Steam, itch and the draft release.

`serve` downloads the latest `actions/runner` once and checks its SHA-256 against the release notes. Then it registers a just-in-time runner for the repo. The runner takes one job and deregisters. `serve` starts a new runner after each job until the watched runs finish, then removes the job workspaces. No runner exists while `serve` is not running, so no job can start on this Mac unasked. A job that nobody serves fails after 24 hours.

The jobs run as the logged-in user, niced, with `caffeinate` holding off sleep. Their environment holds only `HOME`, `PATH`, `USER`, `SHELL`, `TMPDIR` and `LANG`, so none of your tokens reach a step. A workflow that runs on both kinds of runner must keep to these rules on a self-hosted Mac:

- Keep signing material in `RUNNER_TEMP`. Never delete a home directory such as `~/.appstoreconnect`, because it holds your own keys.
- Skip `maxim-lobanov/setup-xcode` and anything else that uses `sudo` (`if: runner.environment == 'github-hosted'`).
- Turn off the `setup-node` pnpm cache (`cache: ${{ runner.environment == 'github-hosted' && 'pnpm' || '' }}`). Otherwise it uploads your whole pnpm store to the Actions cache.
- Delete a temporary keychain in an `if: always()` step. If a job stops before that step, `serve` removes the keychain from the search list when it exits.
- Sign with the SHA-1 of the identity you imported (`security find-identity -v -p codesigning "$KEYCHAIN_PATH"`), not with its name. The Mac's login keychain usually holds an identity with the same name, and `codesign` refuses a name that matches in two keychains as ambiguous.
- Read a Keychain `.p12` export with `/usr/bin/openssl` (LibreSSL). Its RC2-40 encryption fails in Homebrew's OpenSSL 3+, which comes first on the Mac's `PATH`.

`--parallel 2` runs two jobs at once. The jobs then share one keychain search list, so two signing jobs that start at the same second can drop each other's entry. `--keep-work` keeps the workspaces in `~/Library/Caches/hatchkit/mac-runner/slots` for inspection.

## `hatchkit keys`

Manage per-project dotenvx private keys.

```bash
hatchkit keys show <project>   # print DOTENV_PRIVATE_KEY_PRODUCTION from keychain
hatchkit keys push <project>   # upsert the key onto the project's Coolify app
```

Keys are generated at scaffold time, live in macOS Keychain / libsecret under the `hatchkit` service, and are **never** written to git.

## `hatchkit config`

Inspect or modify stored provider config.

```bash
hatchkit config                      # show provider status
hatchkit config add <provider>       # (re-)configure a provider
hatchkit config pause <provider> --reason "<why>" [--since YYYY-MM-DD]
hatchkit config resume <provider>    # check a paused provider again
hatchkit config reset                # clear ALL CLI config (confirmed)
```

`config pause` is for a provider you stopped on purpose, such as a self-hosted GlitchTip you switched off. `hatchkit doctor` shows it as skipped with the reason and date, and does not fail on it. The credentials stay stored. Pausable providers: `coolify`, `hetzner`, `dns`, `cloudflare-workers`, `glitchtip`, `plausible`, `listmonk`, `search-console`, `stripe`, `ses`.

Valid providers: `coolify`, `coolify-github-app`, `ghcr`, `hetzner`, `cloudflare`, `dns`, `cloudflare-workers` (alias of `cloudflare`), `s3`, `glitchtip`, `plausible`, `listmonk`, `ses`, `search-console`, `stripe`, `modal`, `runpod`, `hf`, `replicate`.
