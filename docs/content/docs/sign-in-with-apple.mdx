Sign in with Apple is the `apple-oauth` option of the
[account-security feature](/docs/auth-account-security). It uses better-auth's own Apple
provider. Hatchkit adds the one part better-auth leaves to you: the client secret.

```bash
hatchkit update
```

Tick **auth-account-security**, then **Sign in with Apple button**. The option is off by
default.

## What Hatchkit cannot do

Apple has no API for Services IDs or Sign in with Apple keys. Hatchkit cannot create
them, and it cannot read them back to check them. A person with access to the Apple
Developer account does the portal steps below. You need a paid Apple Developer Program
membership.

Apple also accepts no `localhost` or IP address as a return URL. To try the flow before
you deploy, use a test hostname with HTTPS that reaches your machine.

## What the option writes

| File | What it does |
| --- | --- |
| `packages/server/src/auth/apple-sign-in.ts` | Reads the `APPLE_*` variables, mints the client secret, and builds the provider options |
| `packages/server/src/tests/apple-sign-in.test.ts` | Runs a real better-auth instance against the module |
| `packages/client/src/components/auth/apple-sign-in-button.tsx` | The button on `/login` |

It also patches `auth.ts`, the health router and the login page, and adds the variables to
`packages/server/.env.example` and `docker-compose.yml`.

The button renders nothing until the server has all four required values and the key
parses. A partial set is logged at boot, by variable name and never by value.

## Apple Developer portal steps

Do these in [Certificates, Identifiers & Profiles](https://developer.apple.com/account/resources).
The examples use the made-up bundle ID `com.example.app` and the domain `app.example.com`.

### 1. Find the Team ID

Open **Membership details** in your developer account. The Team ID is ten characters,
for example `ABCDE12345`. This is `APPLE_TEAM_ID`.

### 2. Enable the capability on the App ID

1. Open **Identifiers** and select your app's App ID. If there is none, create one with
   an explicit bundle ID. For a Capacitor app, use the `appId` in `capacitor.config.ts`.
2. Tick **Sign in with Apple** and save.

A web-only app needs an App ID too. The Services ID in the next step is grouped under it.

### 3. Create the Services ID

1. In **Identifiers**, add a new identifier of type **Services IDs**.
2. Give it an identifier such as `com.example.app.signin`. This is `APPLE_CLIENT_ID`.
3. Open it, tick **Sign in with Apple**, and select **Configure**.
4. Set **Primary App ID** to the App ID from step 2.
5. Under **Domains and Subdomains**, add `app.example.com`.
6. Under **Return URLs**, add `https://app.example.com/api/auth/callback/apple`.
7. Save.

The return URL is `BETTER_AUTH_URL` followed by `/api/auth/callback/apple`. It must match
exactly, including the scheme and any trailing slash.

### 4. Create the key

1. Open **Keys** and add a key.
2. Tick **Sign in with Apple**, select **Configure**, and choose the App ID from step 2.
3. Register the key and download the `.p8` file. Apple lets you download it once.
4. Note the Key ID, ten characters, for example `KEY1234567`. This is `APPLE_KEY_ID`.

The contents of the `.p8` file are `APPLE_PRIVATE_KEY`. Treat the file as a secret.

### 5. Register your sending domain with Apple's email relay

A user can choose **Hide My Email**. Your app then receives an address that ends in
`@privaterelay.appleid.com`. Apple forwards mail to it only from senders you register.

Open **Services**, then **Sign in with Apple for Email Communication**, and add each
domain or address your app sends from. Apple checks each domain's SPF record. Without
this step, password-reset and verification mail to these users does not arrive.

## Where Hatchkit expects the values

All five go into the server's environment. `auth/apple-sign-in.ts` reads them from
`process.env` on first use.

| Variable | Value |
| --- | --- |
| `APPLE_CLIENT_ID` | The Services ID from step 3 |
| `APPLE_TEAM_ID` | The Team ID from step 1 |
| `APPLE_KEY_ID` | The Key ID from step 4 |
| `APPLE_PRIVATE_KEY` | The contents of the `.p8` file |
| `APPLE_APP_BUNDLE_ID` | Optional. The native app's bundle ID. Leave it empty for a web-only app |

For production, write them encrypted into `packages/server/.env.production`, then push
them to Coolify:

```bash
pnpm --dir packages/server exec dotenvx set APPLE_CLIENT_ID com.example.app.signin -f .env.production
```

```bash
pnpm --dir packages/server exec dotenvx set APPLE_PRIVATE_KEY "$(awk 'NF {printf "%s\\n", $0}' AuthKey_KEY1234567.p8)" -f .env.production
```

```bash
hatchkit sync
```

The `awk` command joins the key onto one line with literal `\n` sequences. The module
accepts that form and real line breaks alike.

For local work, put the same values in `packages/server/.env.development.local`. That
file is gitignored.

## How it works

- **The client secret.** Apple issues no static client secret. The secret is an ES256 JWT
  signed with your `.p8` key, and Apple refuses one older than six months. The module
  mints a 90-day secret at boot and mints a new one after 30 days. `clientSecret` is a
  getter, so better-auth reads a current secret on every token call. The shipped test
  proves this against a real better-auth instance.
- **Apple's origin.** Apple returns with a cross-site `form_post` from
  `https://appleid.apple.com`. better-auth refuses a POST from an untrusted origin when the
  request carries any cookie. A small plugin adds Apple's origin to better-auth's trusted
  list. It does not add Apple's origin to the CORS list.
- **Identity tokens.** `/sign-in/social` accepts an Apple identity token only when
  `APPLE_APP_BUNDLE_ID` is set, and only with that bundle ID as the audience.

## Native apps

In a Capacitor or Electron shell, the button is disabled with a note. Apple's `form_post`
returns to the web origin, and a shell origin such as `capacitor://localhost` cannot be
that origin.

The server half of a native sign-in is in place. A native app sends the identity token
from Apple's native sheet to `/sign-in/social`:

```json
{ "provider": "apple", "idToken": { "token": "<identity token>", "nonce": "<nonce>" } }
```

better-auth verifies the token against Apple's keys, creates the session, and `bearer()`
returns the session token on `set-auth-token`. Set `APPLE_APP_BUNDLE_ID` first.

The shell half is not part of Hatchkit yet. It needs:

1. A native Sign in with Apple plugin, for example `@capacitor-community/apple-sign-in` or
   `@capgo/capacitor-social-login`.
2. The Sign in with Apple entitlement in the committed iOS project.
3. A random nonce per attempt, passed to the native sheet and sent with the token.

**App Store guideline 4.8.** An iOS app that offers a third-party login, such as Google,
must also offer an equivalent login such as Sign in with Apple. Today the shells disable
both buttons, so the iOS app offers neither. If you make Google sign-in work natively,
make Sign in with Apple work natively in the same release.

## Turn it off or rotate the key

To turn Sign in with Apple off, remove the `APPLE_*` values and run `hatchkit sync`. The
button disappears. Existing users keep their accounts.

To rotate the key, create a new key in the portal and set the new `APPLE_KEY_ID` and
`APPLE_PRIVATE_KEY`. Run `hatchkit sync`, check a sign-in, then revoke the old key.
