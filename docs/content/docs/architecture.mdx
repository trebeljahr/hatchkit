A tour of what happens when you run `hatchkit create`, and how the pieces fit together.

## Repository layout

```
hatchkit/
├─ cli/              # the npm package `hatchkit`
│  └─ src/
│     ├─ index.ts         # top-level command dispatcher
│     ├─ prompts.ts       # interactive ProjectConfig collection
│     ├─ config.ts        # keychain + config.json + provider ensure()
│     ├─ scaffold/        # starter copy + feature strip + ports
│     ├─ provision/       # GlitchTip / Plausible / Listmonk + SES / email / search
│     ├─ deploy/          # terraform, coolify, github, gpu, keys
│     ├─ doctor.ts        # provider health checks
│     └─ utils/           # flags, exec, validation, version
├─ starter/          # full-stack template (in-tree; subtree-merged)
├─ infra/            # Terraform + Coolify scripts (in-tree; subtree-merged)
├─ docs/             # this Next.js + fumadocs site
└─ services/ml/      # pre-built ML service templates
```

## Configuration surface

Three layers, in order of precedence:

1. **CLI flags** (`--yes`, `--config`, `--name`, `--no-github`, `--no-deploy`, `--dry-run`).
2. **Config file** passed via `--config <path>.json` — overrides prompt defaults field by field.
3. **Interactive prompts** — fill anything still unset.

The resulting `ProjectConfig` (project name, domain, features, ML selection, deploy target, ports, …) is the single source of truth threaded through the whole `create` flow.

## The `create` pipeline

```
prompts → ensure providers → scaffold app → install deps →
git + github → scaffold infra → terraform → coolify → ML deploy → summary
```

Key properties of the pipeline:

- **Lazy provider ensure.** We only prompt for Hetzner credentials if you actually selected "new VPS". We only prompt for GitHub if you said yes to the repo. Fails **early**, not after files are on disk.
- **Dry-run parity.** `--dry-run` still runs scaffold + infra generation so you see exactly what would change, but never mutates remote systems.
- **Unique ports.** A per-machine ports registry (`config.json#ports`) assigns collision-free `server` / `client` / `nativeHmr` ports so you can run many hatchkit apps locally.
- **Repo URL flows into infra.** GitHub runs **before** infra scaffold so the generated Coolify env has the real `GITHUB_REPO_URL` in it, not a placeholder.

## Project layout: root vs. subdir

By default the deployable lives at the repo root. The manifest sits there too. New Coolify projects use one Docker Image app per service; `--coolify-runtime compose` selects a Compose app. See [Deployment topology](./topology).

When the deployable lives in a sub-folder of a larger repo (a CLI with a sibling marketing site at `site/`, a monorepo with the runtime at `apps/web/`), the manifest's optional `projectSubdir` field captures that path. Hatchkit then:

- writes the Dockerfile + `docker-compose.yml` **inside the subdir** (Coolify's build context), plus the `nginx.conf` a static site's image copies in;
- writes `.github/workflows/*.yml` at the **repo root** with `context: <subdir>` on every build-push step so GitHub Actions only sends the subdir subtree to BuildKit;
- sets Coolify's **Base Directory** to the same subdir on app create / sync, so Coolify clones the repo and builds from `<repo>/<subdir>` rather than from `/`.

`hatchkit adopt` detects this automatically: invoke it from inside a sub-folder (`cd /repo/site && hatchkit adopt`), or from the repo root when the root's `package.json` isn't itself buildable, and the stepper offers a **Project subdir** row pre-filled with the obvious candidate. `hatchkit create` similarly offers a "scaffold into a sub-folder of this repo" option when you run it from inside an existing git repo.

The manifest **always** lives at the repo root, even when `projectSubdir` is set — that way `git rev-parse --show-toplevel` plus a manifest read composes cleanly from any directory inside the repo, and downstream tooling (`hatchkit sync`, `keys push`, `regen-infra`, `destroy`) finds it without knowing about the subdir.

## Secret handling

- **Provider tokens** → OS keychain (`keytar`), service name `hatchkit`.
- **Per-project encryption key** → OS keychain. Used by [dotenvx](https://dotenvx.com) to encrypt `.env.production` in the generated repo. The encrypted file is safe to commit, and should be — it is the at-rest store, see below.

### Where production values live at runtime

Two things are easy to conflate here, so plainly:

- **`.env.production` (dotenvx-encrypted, committed) is the *at-rest store*.** It is what `hatchkit secrets rotate` writes into and what `hatchkit sync` reads. Versioning it in git is what stops the values from existing only on whichever laptop last wrote them.
- **Coolify's environment is the runtime source of truth.** `hatchkit sync` decrypts the at-rest store locally and pushes the resolved values to Coolify. New projects use Docker Image apps by default. Projects that select `--coolify-runtime compose` use the generated `docker-compose.yml` to declare their environment variables.

The encrypted file is **not** shipped into the image, and the server `Dockerfile` deliberately doesn't copy it. Two reasons:

1. It could never cover the client half anyway. Next.js inlines `NEXT_PUBLIC_*` into the browser bundle at image **build** time, so those arrive as Docker build args — no runtime file can affect them.
2. Putting the ciphertext and the key that decrypts it in one image buys little over just holding the resolved values.

`src/config/env.ts` still calls dotenvx, guarded by an `existsSync`, so in a deployed container the call is a no-op and `process.env` already holds everything. The guard is what makes the same file work on a workstation, in CI, and in production.

`hatchkit doctor` fails when a project's repo disagrees with this — when `.env.production` exists but isn't committed (a global `core.excludesFile` listing `.env.production` is the usual cause, and a repo `.gitignore` only beats it with an explicit `!` negation), or when a `Dockerfile` still copies the file into its runtime stage.
- **Provisioned service credentials** → written into the project's env files, never to stdout, plus cached (mode 0600) under `<config-dir>/provisioned/<project>.*.env`. Production values go encrypted into `.env.production`. Development values go into `.env.development.local`, described next.

### Development env files

- **`.env.development` is committed.** The starter's `.gitignore` re-includes it with `!.env.development`, so a machine-wide ignore cannot drop it. It holds only safe local defaults: localhost URLs, the local S3 login, a dev-only auth secret.
- **`.env.development.local` is gitignored** (`.env.*.local`). `hatchkit add` and `hatchkit secrets rotate` write every development credential they provision here: the Listmonk API token, the SES SMTP password, Stripe sandbox keys, and observability secrets with `--enable-dev-obs`.
- **The server loads both.** `src/config/env.ts` reads `.env.development.local` first, then `.env.development`. dotenvx keeps the first value it reads for a key, so the local file wins. Next.js and Vite load `.env.development.local` over `.env.development` on their own.
- **hatchkit never writes a credential into `.env.development`.** A project provisioned before this rule has them there. The next `hatchkit add` or `hatchkit update` moves them into `.env.development.local` and warns, and `hatchkit doctor` fails while any remain. Moving a value does not remove it from git history: if the file was ever committed with it, rotate the credential.

### What hatchkit refuses to commit

Every hatchkit commit (`create`, `adopt`, their GitHub Pages and Cloudflare Workers steps) stages through one guard. It refuses `.env.keys`, `.env.me`, `.env.local` and `.env.*.local`, keystores (`*.keystore`, `*.jks`), `*.p12`, `*.p8`, Terraform state, SSH private keys, PEM files that hold a private key, and any file with a `DOTENV_PRIVATE_KEY_*=<hex>` line, whatever `.gitignore` says. On a refusal it unstages the new files and prints the fix. Every dotenvx write also makes the repo's own `.gitignore` cover `.env.keys` before dotenvx can create the file; a global excludes file does not count, because it protects one machine and no other clone.

`hatchkit doctor` fails on a tracked `.env.keys`, on a committed `.env.development` that holds a provisioned credential, and on an `.env.development.local` the repo does not ignore. A `.env.keys` that was ever committed is burned, even after you untrack it. Run `hatchkit keys rotate <project>` before you write any new value, then rotate every credential it encrypted.

## Scaffolding strategy

Feature stripping, not feature addition.

- The starter is maximal — it contains every feature hatchkit can produce.
- At scaffold time hatchkit **removes** anything you didn't pick (files, package.json deps, env keys, import paths).
- Why: features that can interact (auth + stripe + s3 + websockets) are battle-tested once in the starter rather than N times in hatchkit's scaffold code.

## Update strategy

`hatchkit update` only *adds* features. Removals are refused because the starter can't know which parts of the user-owned code path actually use the feature. Remove manually + update `.hatchkit.json`.

## Testing

`pnpm test` inside `cli/` runs a scaffold matrix: a dozen feature combinations, scaffolded into a temp dir, typechecked and lint-checked. CI runs the same matrix on every push.
