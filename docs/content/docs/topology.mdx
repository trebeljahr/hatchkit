title: Deployment topology
description: How hatchkit lays a project out across Coolify applications, why /api routing works the way it does, and how to repair a project deployed before 0.2.19.
---

Every hatchkit project records a **topology** in `.hatchkit.json`. It is the
single field `create`, `adopt` and `sync` all read to decide which Coolify
applications exist and which domains hang off them.

```json
{
  "topology": "single-origin"
}
```

| Value | Coolify apps | Front end | API | Datastores |
|---|---|---|---|---|
| `single-origin` (default) | one, named `<name>` | `https://<domain>` | `https://<domain>/api` | `mongo` / `redis` services in the same compose |
| `split` | two, `<name>-client` + `<name>-server` | `https://<domain>` | `https://api.<domain>` | Coolify-managed databases |

Manifests written before the field existed are treated as `single-origin`.
That is what every earlier hatchkit run actually deployed, so the default
preserves whatever is currently live. `split` is never inferred — nothing on
disk distinguishes "should be split" from "is single-origin", and guessing it
would re-point a running project at a subdomain with no DNS record.

Pick one at scaffold time:

```bash
hatchkit create --topology=split
```

Or answer the **Deployment topology** step in the interactive flow.

## Rolling deployments and the runtime

A second field, `coolifyRuntime`, decides how each service runs on Coolify.
It determines whether Coolify can overlap application revisions during a deploy.

| Value | Coolify apps | What a deploy does |
|---|---|---|
| `image` (default for new projects) | one **Docker Image** app per service | Starts the new container, waits for its health check, then stops the old one. Continuity also requires readiness, draining and compatible shared state. |
| `compose` | one **Docker Compose** app | Stops the old container, then starts the new one. The site is down until the new process listens. |

Coolify only does rolling updates for Docker Image, Dockerfile, Nixpacks and
Static apps. It has none for Docker Compose apps. So the fix is one Docker
Image app per service, each pulling the image GitHub Actions pushes to GHCR.

The health check does three jobs:

- Coolify waits for it before it removes the old container.
- Traefik sends no traffic to a container that is not healthy yet.
- A new container that never turns healthy is removed. The old one keeps serving, and the deploy fails.

Coolify runs the check inside the container with `curl` or `wget`. Alpine
images have `wget`. The scaffolded Debian images install `curl`. An image
without either fails every deploy, and the old container stays up.

#### Removing the old container

Traefik sends traffic to a container until the container has exited. So when
Coolify stops the old container, the requests sent to it in that moment fail
with a 502, or hang until they end in a 504.

The Dockerfiles hatchkit writes drain the old container first. On
`docker stop`, the container answers the health check with a 503 and keeps
serving every other request. Docker marks it unhealthy after 5 failed checks,
and Traefik stops sending it traffic. The container closes 20 seconds after
the stop (`SHUTDOWN_DRAIN_SECONDS`).

The drain depends on hatchkit's health-check timing: a check every 2 seconds,
5 retries, and a 15-second start period. `hatchkit doctor` reports an app with
other values, and `hatchkit sync` sets them. The first deploy after a change
still stops a container that has no drain.

A compose deploy stops the old container before it starts the new one. The
compose files set `SHUTDOWN_DRAIN_SECONDS=0`, because a drain there only
delays the restart.

Under `image`, the API is always a separate app, so mongo and redis are
Coolify-managed databases for both topologies:

| Topology | Apps |
|---|---|
| `single-origin` | `<name>-client` at `https://<domain>`, `<name>-server` at `https://<domain>/api` |
| `split` | `<name>-client` at `https://<domain>`, `<name>-server` at `https://api.<domain>` |
| static or backend-only | one app, `<name>` |

A manifest without the field is read as `compose`, because that is what it
was deployed as. Choose at scaffold time with `--coolify-runtime image|compose`.

### Moving a deployed project

```bash
hatchkit migrate-runtime --dry-run    # in the project directory
hatchkit migrate-runtime
```

It creates the Docker Image app next to the compose app, with the same image,
env and port on a verification hostname. It deploys it while the old app keeps
serving and checks it through Traefik. Adding public hostnames requires a second
deployment to activate their routing labels. It verifies that deployment and
the public health routes before stopping the old app and pointing the
repo's deploy secret at the new one. The old app stays, stopped:
`--rollback` starts it again, `--cleanup` deletes it.

It refuses a compose app that holds data — a mongo, postgres or redis service,
or any volume. That data lives in the old app's Docker volume and would not
follow. Plan a separate data migration, backup and restore drill before changing
its runtime. Provisioning a managed database does not transfer existing data.

### WebSockets and shared state

An existing WebSocket closes when its server exits. The client must reconnect,
authenticate, rejoin its rooms and refetch authoritative state. The starter's
`RoomSocket` helper gates actions until its `onResync` callback succeeds. Use that
callback to read durable application state; adopting the helper without a real
snapshot callback does not restore a running game or pending business action.

The `websocket` and `client-core` features both require Redis in production.
Room events and per-user sync invalidations cross replicas through Redis;
room presence uses expiring leases so crashed replicas disappear. Readiness
requires acknowledged subscriptions, and transport recovery forces a refetch.
Use a dedicated Redis instance per project: Redis database numbers do not
isolate Pub/Sub channels, and these starter channels are not project-namespaced.

Redis Pub/Sub is not durable history. Persist important actions and snapshots in
the database, with stable action IDs and server-side deduplication where retrying
could duplicate a write. Room messages alone provide neither replay nor
exactly-once execution. During overlap, old and new clients, servers and schemas
must remain compatible. Use additive migrations; process-local game state and
unrenewed job leases need an application-specific handoff design.

The optional offline mutation queue can retry a create after the original write
committed but its response was lost. The example `items.create` endpoint has no
idempotency-key contract. Before using queued creates across releases, add a
stable key on the initial send and server-side deduplication, then test a lost
response followed by replay against the replacement server.

The shared room presence protocol is a compatibility boundary. Earlier starter
servers do not register shared leases, so overlapping them with the new server
cannot produce complete presence snapshots. The new health response advertises
`roomProtocol: 2`. First adoption requires a controlled reconnect and state
handoff; only subsequent releases with a compatible room protocol qualify for
the usual rolling acceptance test.

Before enabling rolling releases for an existing app, test an authenticated
browser session, cross-replica delivery, reconnect and state convergence, an
accepted long request, an unhealthy candidate and rollback through the actual
proxy. Sample HTTP throughout the replacement and verify served image versions.
Unit tests and a healthy container badge do not establish those properties.

`hatchkit doctor` names every app of the project whose deploys still take
the site down.

## single-origin

One Coolify application running the project's `docker-compose.yml`, with all
four services (`server`, `client`, `mongo`, `redis`) inside it. Routing:

```
client → https://<domain>
server → https://<domain>/api
```

Both entries live on the same host, so the browser only ever talks to one
origin. That means no CORS preflights, no cookie-domain configuration, and one
DNS record. WebSockets ride the same route: `wss://<domain>/api/ws` matches the
`/api` router, and Traefik proxies the upgrade transparently.

Two Coolify behaviours make this work, and both bit hatchkit before 0.2.19:

**Path routing needs prefix-stripping turned off.** Coolify turns a URL path
into a Traefik ``PathPrefix`` rule, but it also attaches a `stripprefix`
middleware for any path other than `/`. With that on, a request for
`/api/health` arrives at Express as `/health` and 404s. hatchkit sets
`is_stripprefix_enabled: false` on any app whose routing uses a path. The field
is not accepted on Coolify's create endpoints, so it goes out as a follow-up
PATCH — and it is write-only, so hatchkit pushes it with every update rather
than trying to read it back.

**Router priority resolves itself.** Traefik's default rule priority is the
length of the rule string, so ``Host(`x`) && PathPrefix(`/api`)`` outranks
``Host(`x`) && PathPrefix(`/`)`` on the same host. No explicit priority needed.

## split

Two Coolify applications built from the two GHCR images:

```
<name>-client → https://<domain>
<name>-server → https://api.<domain>
```

Choose this when the API needs to scale, restart or roll back independently of
the front end, or when something outside the browser app is a first-class
consumer of it.

What it costs you:

- **A second DNS record.** `api.<domain>` needs its own A record. `adopt`
  upserts it when a DNS provider is configured; `create` prints the record for
  you to add, because Terraform owns the bare domain's record and doesn't know
  about this one.
- **Cross-origin.** The client's bundle is built against `https://api.<domain>`,
  so the server's CORS allow-list and better-auth `trustedOrigins` have to
  cover the front end's origin. hatchkit keeps `FRONTEND_URL` on the bare
  domain (that's what `getTrustedOrigins()` builds from) and points
  `BETTER_AUTH_URL` / `AUTH_URL` at the API host.
- **Managed datastores.** The two applications get separate Docker networks, so
  a `mongo` or `redis` declared in either half's compose is unreachable from
  the other. hatchkit provisions them as Coolify databases and writes
  `MONGODB_URI` / `REDIS_URL` into the encrypted `.env.production`.
- **Two compose files.** `docker-compose.client.yml` and
  `docker-compose.server.yml`, each declaring one service. Pointing both
  applications at the root `docker-compose.yml` would run the whole stack
  twice. The root file stays put — it's still what `docker compose up` gives you
  locally.

hatchkit also accepts `-frontend` / `-backend` (and `-web` / `-api`) as lookup
aliases, so a hand-rolled pair under those names is reconciled in place rather
than shadowed by a second, empty application.

## Checking what's actually deployed

`hatchkit sync --dry-run` is read-only. It prints the topology it resolved,
where that value came from, the services your compose file declares, and a
before/after diff of the routing:

```bash
hatchkit sync --dry-run
```

```
  streaks → streaks.trebeljahr.com
    topology: single-origin (manifest declares topology "single-origin")
    compose:  docker-compose.yml — services: server, client, mongo, redis

  streaks (qr7yhl7j… · compose)
    build pack: dockercompose
    · docker_compose_domains:
        before: client=https://streaks.trebeljahr.com, server=https://api.streaks.trebeljahr.com/ws
        after:  client=https://streaks.trebeljahr.com, server=https://streaks.trebeljahr.com/api
    · strip_prefix → false (write-only in Coolify's API; pushed with any update)
```

`hatchkit doctor` reports the same thing offline.

## Repairing a project deployed before 0.2.19

**Symptom:** the front page loads but `https://<domain>/api/...` returns a
redirect or a 404 from Next.js — or the whole domain 503s.

**Cause:** Coolify stores `docker_compose_domains` as a *map keyed by service
name*. Older hatchkit sent four separate entries for the `server` service, so
Coolify kept only the last one and silently discarded the rest. Every project
ended up routing `https://api.<domain>/ws` — a subdomain with no DNS record —
and nothing at all on `https://<domain>/api`. Several FQDNs for one service
have to be comma-joined into a single entry instead.

The fix needs no hand-editing in Coolify:

```bash
cd <project>
hatchkit sync --dry-run
```

Confirm the "after" line routes `server` to `https://<domain>/api` and that
every service name it mentions appears in your `docker-compose.yml`. Then:

```bash
hatchkit sync --deploy
```

`--deploy` matters. Coolify regenerates a container's Traefik labels when it
deploys, not when the application record is PATCHed — without it the corrected
routing sits in the database while the live containers keep serving under the
old labels.

Verify:

```bash
curl -fsS -o /dev/null -w '%{http_code}\n' https://<domain>/api/health
```

### If sync refuses

```
✗ REFUSING to sync — routing names compose service(s) "app" that
  docker-compose.yml does not declare
```

That is the guard working. Coolify answers a routing PATCH for a service that
isn't in the compose with a **200 OK** and then emits no Traefik labels at all,
so the application 503s every request — a silent outage that reads as a
successful sync. Set `publicService` in `.hatchkit.json` to one of the services
the error lists, then re-run.

### If sync stops on the deployed ref

```
✗ Coolify deploys origin/main — origin/main @ 26fdc06 "Initial scaffold"
    docker-compose.server.yml is missing from origin/main — it exists locally but has never been pushed
```

Under `split` the two halves build from `docker-compose.client.yml` and
`docker-compose.server.yml`, which are new files. Coolify clones the remote
branch, so until they are pushed every deploy fails — and it fails with a git
error about credentials rather than about the missing file. `git push` and
re-run.

### If Coolify reports a domain conflict

A 409 means another Coolify resource already claims the domain. Check that it
isn't a live app you still need; if it's a stale one for this same project,
re-run with `--force`.

### The client bundle also has to be rebuilt

`NEXT_PUBLIC_API_URL` is inlined into the browser bundle when CI **builds** the
image — runtime env on the deployed container cannot change it. If you switch
topology, `hatchkit regen-infra` refreshes the build-args in
`.github/workflows/build-and-deploy.yml`, and the next push rebuilds the image
against the new API host.

## Verifying that the deploy actually landed

Every scaffolded pipeline ends with a step that proves the deployed artefacts
are the ones the run built:

```
✓ api https://api.<domain>/api/health reports 4f2c9ab…
✓ web https://<domain>/version.json reports 4f2c9ab…
✓ client is built against https://api.<domain>
✓ CORS allows https://<domain>
```

Before this existed, the pipeline's final assertion was an HTTP 200 from the
Coolify deploy POST — an assertion about Coolify's *inbox*. It does not wait
for the deployment (the POST returns as soon as the work is queued) and it
never looks at what ends up running. Three real failures shipped green through
that gap, none of them visible from CI, from GHCR, or from the Coolify
dashboard: a container that kept the previous image because the compose file
named a mutable tag, a client image built with an empty `NEXT_PUBLIC_API_URL`,
and a server crash-looping behind a proxy that answered 503 while Coolify
reported `running:healthy`.

How it works: both images bake the commit in as a `COMMIT_SHA` build arg. The
server reports it as `version` on `/api/health`; the client writes
`/version.json` carrying `{"commit", "apiUrl"}`. The deploy job pins
`SERVER_IMAGE` / `CLIENT_IMAGE` to the immutable `:<sha>` tag, deploys, then
polls both artefacts (cache-busted — a CDN hit would return exactly the stale
copy being tested for) until they report the pushed commit.

A project brought in with `hatchkit adopt` builds one image, not two, so its
compose reads a single `APP_IMAGE` and its deploy job pins that one variable.
Everything else about the gate is the same.

The gate degrades with the project's shape. A `backend` project has no
`version.json` to poll; a `static` one has no `/api/health`; a `single-origin`
project is same-origin, so the CORS assertion is skipped. What it will not do
is pass having checked nothing: if a deploy fired and both
`HATCHKIT_WEB_URL` / `HATCHKIT_API_URL` are empty, the step fails and says so.

### If the gate fails

```
::error::web https://<domain>/version.json never reported 4f2c9ab — the deploy did not land.
::error::last seen: 8813def
```

The deploy was accepted and something older is still serving. In order of
likelihood: the deploy never ran (check the Actions tab for a run on this
commit), the deploy ran against a mutable tag and Docker reused the image it
already had, or the deploy failed after being accepted (read the Coolify
deployment log).

```
::error::client was built against 'https://old.example.com', expected 'https://api.example.com'
```

The image is the right commit with the wrong API host baked in. `NEXT_PUBLIC_*`
is inlined at build time, so this is a build-args problem, not a runtime one —
`hatchkit regen-infra` refreshes them and the next push rebuilds.

### The same check outside CI

`hatchkit doctor` runs it against `origin/<branch>`, which catches the case CI
cannot: a deploy that silently never happened at all, so there is no failing
run to look at.

```
✗ Project <name> (deployed version) — web @ 8813def — origin/main @ 4f2c9ab is not what is running
```

A project whose images predate `COMMIT_SHA` reports no version at all. That is
a `skip`, not a failure — run `hatchkit regen-infra` and push to rebuild.

### Retrofitting an older project

`hatchkit update` and `hatchkit regen-infra` both add the whole set: the
`pull_policy: always` lines, the `COMMIT_SHA` build args, the version stamps,
and the gate itself. They share one table, so neither can retrofit a subset —
a project that got the gate without the stamps would fail every deploy on a
check its own images cannot satisfy.
