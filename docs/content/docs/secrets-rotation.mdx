description: Two kinds of rotation — dotenvx keypair vs. provider credentials — and how to use `hatchkit secrets rotate` to swap per-project and shared credentials safely.

Hatchkit has two distinct rotation flows. They live next to each other and sound similar, but they touch different things and you reach for them in different situations.

## Two kinds of rotation

### dotenvx keypair rotation — `hatchkit keys rotate`

Re-encrypts `.env.production` with a new `DOTENV_PRIVATE_KEY_PRODUCTION`. Under the hood: `dotenvx rotate -f .env.production`, prune `.env.keys` back to the new key, update the macOS Keychain / libsecret entry, then push the new private key to Coolify and the GitHub Actions secret store. The **provider credentials inside the env file do not change** — every value is decrypted with the old key and re-encrypted with the new key. This is the right command when the encryption key itself is compromised (lost laptop, leaked `.env.keys`, suspected keychain dump) or when you want a scheduled rotation of the at-rest encryption layer.

### Provider credential rotation — `hatchkit secrets rotate`

Generates new third-party credentials (a new OpenPanel write client, a new GlitchTip DSN, etc.) by talking to each upstream provider's API, and writes them into the encrypted env file. The **dotenvx keypair is unchanged** — the file is still encrypted with the same `DOTENV_PRIVATE_KEY_PRODUCTION`. Each adapter runs in two phases (mint new → verify → revoke old), so a verify failure leaves the old credential live and stashes a rollback blob in the keychain. This is the right command when a specific upstream credential is compromised (an OpenPanel secret leaked into a log, a GlitchTip DSN posted in a screenshot) or as part of scheduled per-provider rotation.

The two flows are independent, but their order matters. If both the keypair and the upstream credentials need rotating, run `hatchkit keys rotate <project>` first, commit the re-encrypted `.env.production`, then run `hatchkit secrets rotate`. The other order publishes the new credential: it is encrypted to the leaked key, and the next push makes it readable from history. `secrets rotate` enforces this (see [Order rule](#order-rule-keypair-first)).

## When to use which

| Scenario | `keys rotate` | `secrets rotate` |
|---|---|---|
| `.env.keys` accidentally committed to git (even once, even removed later) | yes, first | yes (after keys, plus `--global` for shared credentials) |
| Laptop with keychain access lost / stolen | yes | yes (after keys) |
| Single upstream provider key leaked in a log | no | yes (`--providers=<that-one>`) |
| Ex-team-member offboarding | yes | yes |
| Scheduled at-rest encryption rotation (quarterly) | yes | no |
| Scheduled provider key rotation (quarterly) | no | yes |
| Suspected upstream provider breach | no | yes |
| Migrating dotenvx versions | yes | no |

For partial-revoke cases (only one provider compromised), `hatchkit secrets rotate <project> --providers=<name>` swaps only that adapter and leaves the rest alone. For partial deploy-target pushes (e.g. rotate locally but don't touch Coolify yet), use `--push-targets=none` or `--push-targets=gh`.

Some credentials are not per-project. hatchkit copies its global SES key and ListMonk API token into every project that sends mail. `hatchkit secrets rotate <project>` never rotates those; its plan lists them under "Shared credentials". Rotate them with `hatchkit secrets rotate --global ses` and `--global listmonk` (see [Global credentials](#global-credentials---global)).

## `hatchkit secrets rotate` — command reference

```bash
hatchkit secrets rotate <project> [flags]
hatchkit secrets rotate --global <ses|listmonk> [flags]
```

Per project: `<project>` is the project slug (matches `.hatchkit.json#name`), and the orchestrator resolves the project directory from the current working directory. With `--global`, no project is named: the command finds every consumer itself.

### Flags

| Flag | Default | Effect |
|---|---|---|
| `--env <scope>` | `production` | Scope the rotation. Only `production` is supported today. |
| `--providers <list>` | `all` | Comma list of adapter names, or `all`. Validated against the live registry — unknown names error cleanly. |
| `--push-targets <list>` | `both` | Comma list of `coolify`, `gh` (alias `github`), or `both` / `none`. Only keys a target already holds are updated: a Coolify env var or Actions secret with that name. Nothing new is created there. |
| `--revoke-old <policy>` | `after-verify` | `after-verify`: revoke old credential only after verify succeeds (global: after every consumer is updated). `never`: leave old credential live. `immediate`: per project, revoke before verify; global, right after verify and before the fan-out. |
| `--keys-rotated` | off | You rotated the dotenvx keypair after a `.env.keys` reached git history. Lets an undecidable history through. A committed key that still encrypts `.env.production` refuses regardless. |
| `--push-gh <owner/repo>` | auto-detected | Per project: override the GitHub repo for the Actions secret push. Alias: `--repo`. |
| `--global <ses\|listmonk>` | — | Rotate a shared credential and update every copy. |
| `--projects-root <dirs>` | `$HATCHKIT_PROJECTS_ROOTS`, else `~/projects` and `~/work` | Global: comma list of directories whose direct children are scanned for `.hatchkit.json`. |
| `--exclude <names>` | — | Global: project slugs or Coolify app names to leave alone. |
| `--resume` | off | Global: finish an interrupted rotation from its rollback blob. |
| `--yes` | off | Global: skip the confirmation prompt. |
| `--dry-run` | off | Print the plan (providers or consumers, env-key names, deploy targets, side effects) without minting, writing, or pushing. |
| `--json` | off | Emit one NDJSON line of the audit on stdout. Names + outcomes only — never credential values. |

### Examples

Rotate every detected provider, push everywhere previously configured:

```bash
hatchkit secrets rotate raptor-runner
```

Preview the plan without mutating anything:

```bash
hatchkit secrets rotate raptor-runner --dry-run
```

Rotate only OpenPanel (e.g. a leaked write-client secret):

```bash
hatchkit secrets rotate raptor-runner --providers=openpanel
```

Rotate locally only — no Coolify or GitHub push (you intend to handle the fan-out yourself):

```bash
hatchkit secrets rotate raptor-runner --push-targets=none
```

Emergency leak race — revoke the old credential before verifying the new one. Use when you are racing an exfiltrated key and accept the small window where neither old nor new may work:

```bash
hatchkit secrets rotate raptor-runner --revoke-old=immediate
```

Audit-friendly rotation — mint the new credential, push it, verify it, but leave the old one live for a later manual revoke (useful when you need a window to update consumers that pin the old key):

```bash
hatchkit secrets rotate raptor-runner --revoke-old=never
```

Rotate the global SES key and ListMonk token after a leak. Look at the plan first:

```bash
hatchkit secrets rotate --global ses --dry-run
hatchkit secrets rotate --global ses
hatchkit secrets rotate --global listmonk
```

Machine-readable output for CI:

```bash
hatchkit secrets rotate raptor-runner --json | jq '.adapters[] | {provider, verificationResult, oldRevoked}'
```

## Supported providers

The registry today:

| Adapter name | Label | Env keys rotated | Verify probe | Notes |
|---|---|---|---|---|
| `openpanel` | OpenPanel write client | `OPENPANEL_CLIENT_ID`, `OPENPANEL_CLIENT_SECRET`, `PUBLIC_OPENPANEL_CLIENT_ID` | `GET /manage/projects` with the new client | Additive rotation — the new client exists alongside the old until revoke runs. |
| `glitchtip` | GlitchTip DSN | `GLITCHTIP_DSN`, `PUBLIC_GLITCHTIP_DSN` | `POST /api/<project-id>/store/` with a minimal Sentry envelope | Split-surface projects rotate two distinct DSNs (one per GlitchTip project: `<name>-server` and `<name>-client`). Non-split surfaces share a single DSN across both env vars. |
| `r2` | Cloudflare R2 S3 key pair | `<R2\|S3\|AWS>_ACCESS_KEY_ID` / `_SECRET_ACCESS_KEY`, and per-bucket `R2_<BUCKET>_*` | `ListObjectsV2` (1 key) with the new pair against the project's endpoint, retried while the token propagates | The access key id is the R2 account token id; the secret is sha256 of the token value. The new token copies the old token's buckets and permissions (from its policy, else the manifest). The old token is deleted after verify. `.hatchkit.json`'s `tokenId` moves to the new token, so `hatchkit provision s3` keeps reusing it. |
| `local-secrets` | Locally generated secrets | `CRON_SECRET`, `NEWSLETTER_TOKEN_SECRET`, `BETTER_AUTH_SECRET`, `AUTH_SECRET` — only those already in `.env.production` | skipped | New value: 32 random bytes as hex. Nothing upstream to revoke. Side effects, shown in the plan: the auth secret signs every user out and invalidates enrolled TOTP two-factor; the newsletter secret breaks confirm and unsubscribe links already sent. |

The Stripe webhook signing secret is not rotated. Stripe rolls it only from the dashboard; the API has no roll, and a second endpoint would double-deliver events.

Run `hatchkit secrets rotate <project> --dry-run` to see which adapters detect against your project — `envPresence` (the union of names found in `.env.development` and `.env.development.local`, both plain, and `.env.production` decrypted) is the canonical signal each adapter consults.

## Global credentials (`--global`)

A global credential is one upstream secret that hatchkit copies into many places. Rotating it means minting once, then updating every copy.

| Name | Credential | Consumers hold | Rights needed |
|---|---|---|---|
| `ses` | IAM user `hatchkit-ses` (keychain `ses:access-key-id` / `ses:secret-access-key`) | `SES_SMTP_USERNAME` (the access key id), `SES_SMTP_PASSWORD` (derived from the secret), ListMonk's SMTP login | The IAM user must manage its own keys, or you paste a one-off admin key |
| `listmonk` | An API user (keychain `listmonk:api-token`, config `providers.listmonk.apiUser`) | `LISTMONK_API_USER` + `LISTMONK_API_TOKEN` | A one-off ListMonk API user with `users:get` + `users:manage` |

### How consumers are found

- **Local projects.** hatchkit scans the direct children of each project root for `.hatchkit.json`. It matches on env key names in `.env.production` and `.env.development`, not on the manifest's email setting. It then decrypts the value in memory and rewrites a project only when it holds the OLD credential. A project wired to another account is left alone.
- **Coolify apps.** hatchkit lists every application's env var names and updates apps that hold a consumer key. Coolify's API returns values too; hatchkit drops them inside the client and never prints or keeps one.
- **Services.** For `ses`, the ListMonk SMTP server that logs in with the old key gets the new username and password. Other SMTP servers and the from-address stay as they are. ListMonk's API masks every stored SMTP password, and its per-key write stores the list as sent. So when another SMTP server has a password, hatchkit cannot write the list back without breaking it: the run names the fields to paste in Settings → SMTP and holds the revoke until `--resume`.

Each consumer gets every key of the credential, also a key it did not hold: the values work only together. The plan marks such a consumer with "adds <key>". GitHub Actions secrets are the exception: hatchkit updates only the ones a repo already holds, and says which key is missing.

A project whose dotenvx key is in git history is skipped with the reason. A plaintext `.env.development` is rewritten only when git ignores it.

### Order of a global run

1. Check rights. Ask for a one-off admin credential when needed and the terminal is interactive. It is never stored.
2. Find consumers and show the plan. Ask for confirmation unless `--yes`.
3. Create the new credential and verify it.
4. Store it in the keychain.
5. Update every consumer.
6. Revoke the old credential, only if every consumer was updated. Then check, with retries, that the new credential still works and the old one no longer does.

A project skipped because its dotenvx key is in git history still holds the old value in `.env.production`. It holds the revoke too: revoking would break it in production. Rotate its keypair, then `--resume`. `--revoke-old=immediate` revokes regardless and leaves that project broken until then.

If the revoke cannot prove its result, the run prints the state it measured instead of a guess, and the exact steps to recover. When the new credential no longer works after the revoke, the outcome is `broken`: consumers are down until those steps are done.

If a consumer fails, the old credential stays active and a rollback blob stays in the keychain under `secrets-rollback:@global:<name>`. Fix the failure, then run `hatchkit secrets rotate --global <name> --resume`. It updates the consumers that still hold the old value and revokes the old credential.

hatchkit never commits or pushes. The run ends with the repos to commit and the Coolify apps to redeploy. Until they redeploy, apps keep the old value, and after the revoke that value fails.

### SES: IAM rights

`hatchkit-ses` sends mail and nothing else, so it cannot create or delete its own access keys. Give it exactly that with this inline policy (IAM → Users → hatchkit-ses → Add permissions → Create inline policy → JSON):

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "RotateOwnAccessKeys",
      "Effect": "Allow",
      "Action": [
        "iam:CreateAccessKey",
        "iam:DeleteAccessKey",
        "iam:ListAccessKeys",
        "iam:UpdateAccessKey"
      ],
      "Resource": "arn:aws:iam::*:user/${aws:username}"
    }
  ]
}
```

Or run the command in a terminal and paste a one-off admin access key when asked (see [Pasting a one-off admin credential](#pasting-a-one-off-admin-credential)). Deactivate that key afterwards if you created it for this run.

IAM allows two access keys per user. The rotation creates the second one, verifies it with an SES API call and an SMTP login that sends no mail, then deactivates and deletes the old one. If the user already has two keys, the run stops and names the one to delete.

### ListMonk: replacement user

ListMonk cannot regenerate an API user's token. hatchkit creates a replacement API user, `<name>-rotate-<stamp>`, with the same role, and verifies it with `GET /api/profile`.

The replacement keeps that name. hatchkit never renames it to the old name. ListMonk stores an API user's token in the `password` column, and its `update-user` query (v4.0 through v6.1) sets that column to NULL whenever `password_login` is false, which it always is for an API user. So any update of an API user wipes its token. v6.2 keeps the token, but the rotation has to work on every version from v4.0. On 2026-09-29 a rename left every consumer with a dead token.

So `LISTMONK_API_USER` and `LISTMONK_API_TOKEN` change together. hatchkit writes both into every consumer, also into one that held only the token, and stores both: the token in the keychain, the name in `providers.listmonk.apiUser`. The next rotation of `hatchkit-rotate-202609291130` creates `hatchkit-rotate-<new stamp>`, so the name does not grow.

After the fan-out hatchkit deletes the old user. Then it checks, with retries, that the replacement still authenticates and the old pair no longer does. When a check fails, the run prints what it found: whether the old user is deleted, whether ListMonk accepts the replacement's token, and which consumers hold that token.

If ListMonk rejects the replacement's token after the delete, the outcome is `broken`. Recover like this:

1. ListMonk → Admin → Users → New: type API, the role the run names. Copy the token that ListMonk shows once.
2. Run `hatchkit config add listmonk` and paste that name and token. hatchkit checks them before it stores them.
3. Run `hatchkit secrets rotate --global listmonk --resume`. It writes that pair into every consumer that holds the rejected one, and deletes the rejected user.
4. Commit, push and redeploy the consumers it lists.

`--resume` fans out the pair that the keychain holds, after ListMonk accepts it. It refuses a pair that ListMonk rejects, so it never writes a dead token. This also finishes a run that was fixed by hand in the keychain: the run names any stray replacement user to delete.

Creating users needs `users:get` and `users:manage`. Do not add them to the `hatchkit` role: a leaked token could then create admins. Create a temporary API user with the Super Admin role, paste it when asked, and let hatchkit delete it at the end. After that delete, hatchkit checks again that the replacement authenticates.

### Pasting a one-off admin credential

hatchkit checks each pasted value before it uses it, and prints the result:

- **Shape.** The length and the characters. A ListMonk API token is 32 letters and digits. An AWS access key id is 20 capital letters and digits and starts with `AKIA`. An AWS secret access key is 40 characters. Stray spaces and quotes are named with their position. A value with the wrong shape is refused and asked again, up to three times. The secret itself is never printed.
- **Identity.** `✔ authenticated as <user> (id, type, role)` from ListMonk's `GET /api/profile`, or `✔ authenticated as <arn> (account, user id)` from AWS STS `GetCallerIdentity`.

hatchkit stops before it changes anything when the identity does not fit: a ListMonk token that belongs to another user, the ListMonk user being rotated, a ListMonk role without `users:manage`, an AWS key from another account than the SES key, or the SES user's own key.

## Order rule: keypair first

A new credential is encrypted to `DOTENV_PUBLIC_KEY_PRODUCTION`. If the matching private key is in git history, anyone with the history can read the new value after the next push. So `secrets rotate` refuses when:

- `.env.keys` is tracked by git now, or
- any commit on any ref added a `.env.keys` whose key still derives the current public key.

When a committed `.env.keys` exists but hatchkit cannot tell whether it is current (no public key in `.env.production`, an unreadable blob), it refuses unless you pass `--keys-rotated`. A committed key that is still current refuses even with the flag. `--dry-run` shows the refusal in the plan instead of failing.

The fix is always the same:

```bash
hatchkit keys rotate <project>
git add <the re-encrypted .env.production> && git commit
hatchkit secrets rotate <project>
```

## Adding a new provider adapter

Adapters live one-per-file under `cli/src/secrets/adapters/`. They self-register at import time via `register(adapter)` from `../registry.js`. The orchestrator iterates the registry — adding a new provider is "drop a file, import it from the barrel, done". No switch statements, no central manifest.

### The `ProviderRotator` interface

```ts
// cli/src/secrets/types.ts
interface ProviderRotator {
  readonly name: string;   // stable slug used in --providers=<name>
  readonly label: string;  // human-readable label for log output

  // Pure / read-only. Returns true when this adapter should run.
  // Combines ctx.envPresence with manifest hints.
  detect(ctx: RotationContext): boolean;

  // The env-var names this adapter owns. Returned upfront so dry-run
  // can print them and the orchestrator can collision-check.
  envKeys(ctx: RotationContext): ReadonlyArray<EnvKeySpec>;

  // Read the CURRENT credential so the orchestrator can stash it in
  // the rollback store BEFORE any mutation. Empty values map → the
  // orchestrator downgrades revoke policy to 'never' for this adapter.
  captureOld(ctx: RotationContext): Promise<OldCred>;

  // Mint a fresh credential from the upstream provider. Side-effect-
  // only against the upstream API — do NOT write to disk, keychain,
  // or deploy targets. The orchestrator owns those steps.
  createNew(ctx: RotationContext): Promise<NewCred>;

  // Smoke-test the NEW credential. Return 'skipped' when no cheap
  // probe exists — the orchestrator will not revoke the old key.
  verify(ctx: RotationContext, fresh: NewCred): Promise<VerifyOutcome>;

  // Revoke the OLD credential upstream. Must be idempotent — a 404
  // is success.
  revoke(ctx: RotationContext, old: OldCred): Promise<void>;

  // Optional. `false` when nothing upstream stands behind the value
  // (local-secrets): revoke is skipped and reported as not-applicable.
  readonly revocable?: boolean;

  // Optional. One line per consequence for users, shown in the plan.
  sideEffects?(ctx: RotationContext): string[];

  // Optional. Record the new credential's non-secret ids (the R2 token
  // id in .hatchkit.json) right after the env write.
  recordNew?(ctx: RotationContext, fresh: NewCred, old: OldCred): Promise<void>;
}
```

### Self-registration pattern

At the bottom of each adapter file:

```ts
// cli/src/secrets/adapters/<name>.ts
register({
  name: "<slug>",
  label: "<Human label>",
  detect, envKeys, captureOld, createNew, verify, revoke,
});
```

Then add one line to the barrel so the side-effectful `register` call runs:

```ts
// cli/src/secrets/adapters/index.ts
import "./glitchtip.js";
import "./openpanel.js";
import "./<new-adapter>.js";   // ← add this
```

No orchestrator changes required. Duplicate `name` collisions throw at startup so accidental shadowing is loud.

### Reference example

[`cli/src/secrets/adapters/openpanel.ts`](https://github.com/trebeljahr/hatchkit/blob/main/cli/src/secrets/adapters/openpanel.ts) is the canonical reference. It demonstrates:

- Reading from the adapter-private keychain cache populated by the matching `provision/openpanel.ts` flow.
- Stashing API-call intermediates on `ctx.scratch[ADAPTER_NAME]` so `captureOld` → `createNew` → `verify` → `revoke` don't refetch config.
- Filtering `ENV_KEYS` to whatever is actually present in the project (avoid writing `PUBLIC_*` mirrors into a backend-only repo).
- Additive rotation: mint a new client, verify it, then `DELETE` the old client by id — the new credential exists alongside the old one until revoke runs, which is what makes the rotation crash-safe.

[`cli/src/secrets/adapters/glitchtip.ts`](https://github.com/trebeljahr/hatchkit/blob/main/cli/src/secrets/adapters/glitchtip.ts) shows the same pattern with two extra wrinkles: a verify probe against the upstream's data ingest endpoint (not just a control-plane probe), and a per-env-var handle shape (`<field>:<envKey>`) for split-surface projects that own two GlitchTip projects.

## Safety notes

### dotenvx-encryption requirement

`secrets rotate` writes new credential values into `.env.production` via the canonical `writeProdEnv` helper, which encrypts every value with the project's `DOTENV_PRIVATE_KEY_PRODUCTION`. If `.env.production` is not yet dotenvx-encrypted, the orchestrator prints a yellow warning and proceeds — the rotation will encrypt it going forward, but past git commits may contain plaintext credentials. Run `hatchkit adopt` first to migrate an existing project onto dotenvx.

### `.env.keys` gitignore requirement

The orchestrator **refuses** to run when `.env.keys` is tracked by git, or when git history holds the current key (see [Order rule](#order-rule-keypair-first)). The reasoning is that rotating provider credentials while the dotenvx private key still sits in your git history is theatre — the encrypted `.env.production` is already readable to anyone with repo access. The error message spells out the recovery recipe:

```bash
git rm --cached .env.keys
echo .env.keys >> .gitignore
hatchkit keys rotate <project>
# then retry:
hatchkit secrets rotate <project>
```

### Audit redaction guarantee

The audit shape (`RotationAudit`) carries names + outcomes only — never credential values. Defence-in-depth runs on top: a `redactValues` walker scans every audit object before stdout and replaces strings matching credential heuristics (hex 32+ chars, common prefixes like `sk_` / `whsec_` / `ghp_`, DSN-shaped URLs, anything keyed under `*_SECRET` / `*_KEY` / `*_TOKEN` / `*_PASSWORD` / `*_DSN` / `*_PRIVATE_KEY`) with `[REDACTED]`. Adapter errors are wrapped through `redactErrorMessage` before reaching stderr for the same reason. `--json` output is safe to pipe into logs.

### Two-phase rotation guarantee

Each adapter runs `captureOld → saveRollback → createNew → write envs → recordNew → push targets → verify → revoke (only when verify succeeded)`. A verify failure leaves the **old credential live** and stashes a rollback blob in the keychain under account `secrets-rollback:<project>:<adapter>`. The orchestrator clears the rollback blob only on full success (`verify === 'ok'` AND `oldRevoked === true`). Anything else keeps the blob around for operator inspection.

Adapters that cannot recover the old credential (empty `captureOld` result) silently downgrade revoke policy to `never` for that adapter — the audit picks this up via `revoke-held` and the old credential is not touched.

`--revoke-old=immediate` reverses the order (revoke first, verify second) for emergency leak-race scenarios. The operator accepts the small window where neither the old nor the new credential may work, in exchange for not leaving the old key live for the duration of the verify probe.
